# 变更记录：未加载区块里的罐位改为候选集合

日期：2026-10-17
分支：`fix/tank-slot-candidates`（专家落地改动，主会话复核后统一 commit / push）
状态：**PARTIAL** —— 代码与单测齐备、构建通过；实机项（目的地所在区块未加载时的真实传送）待机主执行

## 改了什么

### 1. 罐位判定拆成纯函数 `payment/TankPlacement`

- 删 `tankPosFor(Level, Waystone)`（全仓仅两个调用方，均已改）。
- 新增 `enum RecordedHalf { UPPER_HALF, LOWER_OR_SINGLE, UNKNOWN }`，表达「石碑把哪个位置记进了 `waystones.dat`」。
- 纯函数 `candidateTankPositions(BlockPos waystonePos, RecordedHalf half)`：
  `UPPER_HALF` → 一个候选（`pos.below().below()`）；`LOWER_OR_SINGLE` → 一个候选（`pos.below()`）；
  `UNKNOWN` → 两个候选（`pos.below()`、`pos.below().below()`，`LinkedHashSet` 去重后保序，正下方优先）。
- 观测层 `candidateTankPositions(Level level, BlockPos waystonePos)`：`Level#isLoaded` 为假即 `UNKNOWN`；
  否则读本格与下方格的状态，`!state.isAir() && below.getBlock() == state.getBlock()` 判为 `UPPER_HALF`，其余 `LOWER_OR_SINGLE`。
- 类 javadoc 补一段，说明为什么不能直接用方块状态判双格：服务端 `getBlockState` 会隐式加载区块，
  客户端在未加载区块读到 `EmptyLevelChunk` 的 `VOID_AIR`，于是「双格石碑」被当成「单格石碑」。

### 2. 服务端按候选找罐、载入必须过预算 `event/XppTeleportHandler`

- `payerAt(...)` 内的 `tankPos = TankPlacement.tankPosFor(...)` + `tankAt(level, tankPos, budget)`
  换成 `tank = tankBelow(level, waystone.getPos(), budget)`；`Payer` 的位置取 `tank.getBlockPos()`（实体真实位置）。
- `tankBelow(ServerLevel, BlockPos waystonePos, PayerBudget)`：先 `residentTankAt(level, candidates)` 命中即返回；
  否则 `budget.requestLoad(TankPoolIndex.key(...), now, REMOTE_PAYER_MEMO_MILLIS)` 否决即返回 null；
  通过后 `level.getChunk(x >> 4, z >> 4, ChunkStatus.FULL, true)`，再 `residentTankAt` 一次。
  预加载用石碑位置算区块（两个候选只差 Y，必同区块），因此一次配额覆盖全部候选。
- `residentTankAt(ServerLevel, List<BlockPos>)`：逐个候选 `level.isLoaded(candidate)` 先判，再 `getBlockEntity`。
  javadoc 说明这个顺序是承重细节：`Level#getBlockEntity` 走 `getChunkAt`（`FULL, true`），先探针否则又变成无预算加载。

### 3. 客户端两个候选都问 `client/XppClientRequirements`

- `tankBelow(...)`：跨维度仍返回 null；先 `TankPlacement.candidateTankPositions(level, waystone.getPos())`，
  任一候选已加载即读实体并 `XppClientTankRegistry.remember(...)`；对每个**本机看不到**的候选
  `XppTankHints.request(...)`（已有答复时幂等）——看得见的槽本身就是答案，不必问服务端。
- 新增包级纯函数 `selectPayerSlot(List<BlockPos> candidates, Predicate<BlockPos> seenHere, Function<BlockPos, Hint> hintOf)`：
  第一轮找「注册表见过的位置」（地面真相），第二轮找「提示算付款方」的——提示不得遮蔽另一候选上真见过的罐。
- 新增 `paysFrom(@Nullable Hint)`：`mayPay()` 且「不是已知空罐」。`payerAt(TankRef)` 改为复用该判定，
  使「空罐不算付款方」只有一个定义（原先在两条 if 里各写一遍）。

### 4. 测试（新增 13 例）

- `src/test/java/com/olynk/waystonexppayment/payment/TankPlacementTest.java`（6 例）：已加载的上半格 / 下半格 / 单格各自唯一解；
  未加载时两个候选的顺序、去重，以及「`UNKNOWN` 的候选集必须包含两个已知答案」（换一种记录方式不能丢答案）。
- `src/test/java/com/olynk/waystonexppayment/client/XppClientRequirementsTest.java`（7 例）：`selectPayerSlot` 的
  注册表优先、首槽无答案即点亮、次槽有罐能被找到、一槽空罐不遮蔽另一槽、`DENIED` 不付款、两槽都无罐不付款。

## 为什么改

`waystones.dat` 记的是石碑的**上半格**，罐在它下方两格。旧逻辑靠「本格与下方格是不是同一种方块」判断石碑是单格还是双格，
再决定罐在下方一格还是两格。这个判断需要区块已加载：服务端读它会顺带把区块拉进来，客户端则拿到空气。
空气 → 判成单格 → 罐位算到石碑自己的下半格，于是池子被写到 `(x, y-2, z)` 这种没人放罐的位置，
真罐的库存永远不参与报价（有时还会因为「附近有罐」把按钮点亮，却在传送时按玩家 XP 扣）。

## 根因

一个事实（石碑占几格、罐在下方几格）被当成「随时可读的当前状态」，但它其实是**存档里的记录**：
未加载时该状态不可观测，不可观测不等于「不存在」。正确做法是把「不可观测」显式建模成第三种答案，
并让它携带两个候选，等到能观测时再收敛。

## 与上一版的对比

| 场景 | 上一版 | 这一版 |
| --- | --- | --- |
| 石碑记录在上半格、区块**已加载** | 罐位 = `y-2`（正确） | 同（唯一候选） |
| 石碑记录在下半格、区块已加载 | 罐位 = `y-1`（正确） | 同（唯一候选） |
| 石碑记录在上半格、区块**未加载** | 罐位 = `y-1`（**错**，池子记到 `NO_TANK`） | 两个候选 `y-1`/`y-2`，命中真罐 |
| 服务端读罐位的开销 | 一次 `getBlockState`（可能隐式加载，绕开配额） | `isLoaded` 探针；只有真要读盘才 `PayerBudget` 一次配额 |
| 客户端未加载时的询问 | 只问一个槽 | 两个槽都问（`MAX_SLOTS` 内），由纯函数裁决 |
| 网络协议 | v4 | v4（无变化） |

## 风险与未覆盖

- **实机未验**：需要在客户端实机做一次「目的地所在区块未加载」的传送，确认池子落到真槽位（例如 `(1186,64,1212)` 而不是 `(1186,65,1212)`）。
- `RecordedHalf` 的观测层（`isLoaded` + 方块状态比较）没有单测：需要 `Level` 实例，只测了它下面的纯函数。
- 候选只有两个且必须同区块：罐若摆在别处（不紧邻石碑下方）仍读不到，这是既有摆放规则的限制，不是本轮引入。
- 跨维度仍不覆盖（客户端不加载该维度），行为与上一版一致。
- 池索引仍以石碑位置为键、只在载入后写入真槽位；历史数据里已经写坏的 `NO_TANK` 条目不会自动修复，
  下一轮载入该区块时才会被覆盖成正确槽位。
