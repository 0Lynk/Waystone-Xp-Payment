# 空罐也要参与预览：为什么「灰→亮」在界面打开期间不生效

日期：2026-10-26
触发：机主实机报告 ——「罐 20 mB、玩家 0，界面灰；从 0 灌到 200，始终灰；关闭界面再打开，亮。反方向（200 抽到 27 以下）当场变灰。」

## 改了什么

`src/main/java/com/olynk/waystonexppayment/client/XppClientRequirements.java`

1. `decorate` 在「源端付款罐、目的地付款罐」都取不到时，新增一次兜底：`payer = readableTank(sourceTank, targetTank)`，
   只要某一端有一个**本客户端读得到**的罐（无论空不空）就把它当成付款方，照常包装 `ClientFluidPaymentRequirement`。
2. 新增两个私有辅助：`readableTank(TankRef, TankRef)` 与 `isReadable(TankRef)`（判据是 `ref.loaded() != null`，
   即方块实体在本客户端已加载、读数实时）。
3. `decorate` 的 javadoc 从「when a tank below the source could pay」改成「when a tank is there to pay - empty or not」；
   「没有付款罐」那条日志的注释改成陈述后果（该条目此后固定用 Waystones 自己的判定）。

`src/main/java/com/olynk/waystonexppayment/client/ClientFluidPaymentRequirement.java`

4. 类 javadoc 的「loaded with data」一条补上「a tank that is empty included: a pool of 0 asks the player for the whole cost,
   which is the vanilla rule」。

`src/test/java/com/olynk/waystonexppayment/payment/PaymentSplitTest.java`

5. 新增 `anEmptyPoolIsExactlyTheVanillaRule`：`compute(27, 0, 1, 27)` 必须 `affordable`、`compute(27, 0, 1, 26)` 必须不可付、
   `fluidUsedMb()` 为 0。它守的是本次兜底的**前提**——空罐不会比原版 XP 需求更严。

## 为什么

第八轮把置灰改成了「每帧从罐纯派生」，但派生的**入口**仍由条目构建那一刻决定：
`decorate` 里 `payerAt` 把「已加载的空罐」判成「不是付款方」（`XppClientRequirements.java:225-226`，空罐在服务端确实付不了钱，
这条判定对**服务端语义**是对的），于是 `decorate` 走了 `return original`，条目手里是 Waystones 的原始要求。
`mixin/WaystoneButtonClientMixin` 只对 `instanceof ClientFluidPaymentRequirement` 生效，这条条目因此整段跳过——
**没有每帧派生，也就没有「变亮」的另一半**。罐一灌满，条目仍是构建期那次判死的结果，只有关掉界面重开（重建条目）才会重新判定。

反方向之所以正常，是因为「亮→灰」那一次条目是带着非空罐构建的，钩子在，派生就在。

现场日志（`instances\1.21.1\minecraft\logs\latest.log`）坐实了这条链：
`19:10:57 / 19:11:15 / 19:11:19` 三次构建都打 `[client] no payment tank for this entry ... under source=empty tank at 4000, 100, 4000`，
中间 20 秒的灌罐窗口**没有任何** `greyed out` / `re-enabled` 行；`19:11:39` 关掉重开后才出现 `pool 308 XP (cost 27 XP)`。

顺带澄清一个口径：缺陷的边界不是「20 mB vs 200 mB」，而是**空 / 非空**。机主报告的「罐 20 mB」是反方向实验的残余；
若真是 20 mB 起步，条目会被包装，行为正常。

## 备选方案

- **a. 让 `selectPayerSlot` 增加第三轮「罐在但为空」的筛选**：能顺带覆盖远端 hint 报「有罐但池量为 0」的情形。
  否决原因：远端池量只在**构建条目时**问一次（`XppTankHints.TTL_MILLIS = 30_000L`，且过期后不会主动重问），
  包装它换不来「界面打开期间跟着池量走」，只是把一个不变的灰行换成另一个不变的灰行，却扩大了行为面。
- **b. 构建时记住「罐槽存在」，渲染时按槽位现查**：即把「谁付款」也搬到每帧。否决原因：远端槽位每帧要问服务端（包量爆炸），
  而客户端渲染线程不该发网络请求；代价与收益不成比例。
- **c. 不改代码，改为「关了重开」写进文档**：否决原因：这正是机主报的缺陷本身——罐明明灌满了，界面却坚持说付不起。
- **d. 采用 a（兜底 + hint 第三轮）**：见上，暂不采用；如果将来远端罐有了推送式更新（不需要 30 秒轮询），再考虑。

## 意外点

- 「空罐不算付款方」这条规则在**客户端预览**和**服务端选付款方**里是同一条，但正确的处理恰恰相反：服务端要按它挑付款方，
  客户端则应把它当「这个槽位值得盯」的入口。同一个谓词被两处复用，是这次缺陷的来源。
- 包装空罐不会把任何本来能点的条目变灰：`PaymentSplit.compute(cost, pool=0, rate, held)` 退化成 `fromPlayer = cost ≤ held`，
  与原版 XP 需求逐字相同；`anEmptyPoolIsExactlyTheVanillaRule` 把这条前提钉住。
- 兜底只对**本客户端已加载**的罐生效（`isReadable` 判 `loaded() != null`）。远端槽位仍按原样处理：要么 hint 明确能付（原本就包装），
  要么保持 Waystones 自己的判定——这是有意的收窄，避免在无法实时读数的槽位上假装能跟踪池量。

## 验证

- `.\gradlew.bat test --offline` → `BUILD SUCCESSFUL`，**21 suites / 130 tests / 0 failures**（129 → 130）。
- 负向验证：把 `PaymentSplit.compute` 的 `affordable` 改成「空池一律不可付」（`fromFluid > 0 || cost == 0`）→
  `anEmptyPoolIsExactlyTheVanillaRule` 在 `PaymentSplitTest.java:90` 变红；还原后全绿。
- 未覆盖（如实记录）：`decorate` 的兜底分支本身没有单测——它需要客户端 `Level` 与方块实体，测试类路径里没有这些。
  证据靠构建 + 代码走查 + 现场日志复测；复测判据见下。
- 复测判据（机主侧）：罐**严格 0 mB**、玩家 0 XP 打开列表 → 灰；同一界面灌到 ≥27 mB → 当帧变亮，日志出现
  `[client] payment tank for this entry ... pool 0 XP (cost 27 XP)` 与 `[client] re-enabled this entry: tank 27 of 27 XP, player 0 of 0 XP, cost 27 XP`。
