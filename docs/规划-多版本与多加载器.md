# 规划：多 Minecraft 版本与多加载器

> 状态：**暂不启动**（2026-10-31）。mod 还在 0.x，先把功能与接口稳定下来，本文只做决策留档，
> 避免以后重新调研。真正开工前重读一遍，并先核实文末的三个前提。

## 1. 问题拆成两条轴

| 轴 | 含义 | 现状 | 结论 |
|---|---|---|---|
| 版本轴 | 同一加载器下支持多个 Minecraft 版本（1.21.1 → 26.x） | 只有 1.21.1 | 现在就能做，成本可控 |
| 加载器轴 | 同一版本下支持 NeoForge + Fabric | 只有 NeoForge | 成本高且依赖外部条件，押后 |

社区里没有哪个方案同时解决两条轴：版本轴用 Stonecutter，加载器轴用 Architectury 或 MultiLoader。
混为一谈是这类改造最常见的开工错误。

## 2. 社区与主流模组实际在用的七种方案

| 方案 | 管哪条轴 | 做法 | 优点 | 代价 / 已知坑 |
|---|---|---|---|---|
| 每版本独立分支 | 版本 | 每 MC 版本一条长分支，共享代码靠 cherry-pick | 隔离彻底、单分支构建快 | 一个 bug 修 N 次；分支漂移后 cherry-pick 全冲突 |
| **Stonecutter** | 版本 | Gradle 插件，用 `//? if >=26.1 { ... }` 注释做源码级切换，一次生成多版本 jar | 单源、单测试、CI 矩阵天然 | 源码被条件注释污染；IDE 只认一个节点；mixin JSON / `mods.toml` / 依赖坐标仍需人工版本化 |
| Architectury | 加载器 | `common`+`fabric`+`neoforge` 三子工程，用其 API 抹平注册/事件/流体 | 加载器轴最成熟的公共 API | 多一层抽象泄漏；**完全不管版本轴**；跟进上游跳版本滞后 |
| MultiLoader / service loader | 加载器 | 单一 `common` + 两个薄 loader 模块，`common` 只用 SPI + `ServiceLoader` | 无第三方抽象层，控制权全在自己 | 每个平台差异都得自写；`common` 漏进一个 loader import 就整包挂 |
| Sinytra Connector | 加载器（假） | 让 Fabric mod 跑在 NeoForge 上 | 零开发成本的「双平台」 | 运行时垫片不是构建策略；稳定性归第三方；能力语义差异会静默失败 |
| 单仓库多模块 | 两者 | 一仓多个独立 Gradle 子工程，共享 BOM 与 CI | 结构清晰、可独立发版 | 公共代码靠快照 maven/`includeBuild`，跨模块重构贵；易退化成「版本分支换皮」 |
| CI 版本矩阵 | 横切 | Actions 矩阵跑 N 个变体，每格出 jar + 单测 | 任何方案都要 | 构建分钟数与缓存失效；上游 maven 抖动被放大 |

## 3. 本仓库的真实耦合面

**版本轴上是稳的：**

- Waystones `api` 包（`event/XppTeleportHandler.java` 用的 `WaystoneTeleportEvent.Pre` 与 `WarpRequirement`）跨版本最稳。
- 网络 payload 的 `StreamCodec`（`net/XppStatePayload.java`、`net/XppTankHintPayload.java`）从 1.20.5 起是原版 API。
- 数据包 recipe 的 `MapCodec` + `StreamCodec`（`recipe/XpFluidRecipeSerializer.java`）全是原版，也是 KubeJS 的唯一入口。

**版本轴上的两处脆点：**

- `event/XpRequirementScanner.java` 直接引 `net.blay09.mods.waystones.requirement.*`——**不在 api 包**，上游重构需求链就断。
- 两个 mixin（`mixin/WaystonesApiClientMixin.java`、`mixin/WaystoneButtonClientMixin.java`）打在 Waystones 的内部方法与私有字段上，是最脆的一层；`MixinShadowPolicyTest` 是现有的对冲手段。

**加载器轴上是真墙：**

- 流体能力语义不同，不是改名：我们这边是 NeoForge 的 `IFluidHandler`/`FluidTank`/`Capabilities`，Fabric 是 `Storage<FluidVariant>` 的事务模型。
- `DeferredRegister`、`ModConfigSpec`、各类 `...Event` 全是 NeoForge 专有，需逐个适配。
- 低耦合项：FTB Teams 走反射、本就可降级（只有 `ServerLifecycleHooks.getCurrentServer()` 要换成注入）；
  KubeJS 目前零代码，只有 optional 声明。

## 4. 推荐路线

**P0 端口解耦（先做，零行为变化）**

把流体、事件总线、配置收敛到自家 `platform/` 接口，`common` 侧不出现 `net.neoforged`；`FluidTank` 换成自家 `FluidPool`；
`ServerLifecycleHooks` 换注入；`XpRequirementScanner` 去掉对 Waystones 内部包的依赖（改行为探测）。
**这一期在任何方案下都回本**，现有单测当护栏。

**P1 Stonecutter 单源多版本（只用 NeoForge 一线）**

先并 1.21.1 与 26.x 中的一条主线。差异集中在 mixin JSON、`neoforge.mods.toml`、依赖坐标、GUI 渲染。

**P2 加载器轴（条件触发，不预设时间表）**

只有满足「经验流体在 Fabric 侧有等价物」或「有具名 Fabric 整合包需求」才开；届时用 P0 的端口 + MultiLoader 模板。

**明确放弃**

- Sinytra Connector 当交付路线（玩家侧垫片 ≠ 构建策略）。
- 手工维护 ≥3 条版本分支（人力和 Stonecutter 对抗）。
- 1.20.1 当一等公民：Java 17、Forge 47 的流体能力、Waystones 内部类不同形，等于第二个产品。
- KubeJS 原生 schema 插件：数据包配方已够，别为可选软依赖引编译期漂移。

## 5. 产品侧约束（写死，防止越做越多）

**版本矩阵上限 = 2 条线。** 超过就必然出现「最老的线占用最新线的时间」。

| 档 | 版本 | 启动条件 |
|---|---|---|
| 必做 | 1.21.1（NeoForge 21.1.x） | 当前主线，已发 |
| 必做 | 26.x 中整合包普遍采用的那一条 | 两个硬依赖都发布对应版本 |
| 可做 | 1.20.1 | 有**具名**整合包或服主承诺，且做后功能冻结 |
| 可做 | Fabric | 同上，且先确认 Waystones Fabric 侧内部类同形 |
| 不做 | 1.21.2–1.21.9 逐个跟进 | — |
| 不做 | 26.x 每个季度版并行 | — |
| 不做 | 快照 / pre-release | 依赖方根本不发对应版本 |

成本模型（供排期参考）：

- 同族跟进（26.1 → 26.2）：1.5–3 人日
- 跨代新线（→1.20.1 或 →Fabric）：首次 6–15 人日，之后每条线 1.5–3 人日
- **每条新线重测 7 条内置汇率：1.5–2 人日**（`docs/SOP-内置默认数据包.md` 第 8 节要求大版本后重测）
- 一次正式发版：0.5 人日

发布约定（开 P1 时生效）：

- tag/Release 命名沿用 `v<mod 版本>+mc<MC 版本>`，每条线一个 Release，**附件只放一个 jar**（玩家点错 jar 是这类附属最高频的支持请求）。
- 新线的第一版永远是 `-beta.1`，满两周或 3 位独立服主确认后再出正式版。
- README 首屏一行写清 `Supported: 1.21.1 · 26.1`；`neoforge.mods.toml` 的 `versionRange` 保持收窄，让加载器替我说「不」。

止损线：

1. 新线 90 天下载量 < 主线 5% → 冻结（只修崩溃），下季度下线。
2. 一个掉版周期内两个硬依赖任一没出对应版本 → 不启动，也不预先投入。
3. 一次移植超预估 2 倍且未过实机验证 → 停下回单线，结论写进 docs。
4. 单季度维护占用 > 可支配时间一半 → 先停最老的线，不停最新的线。
5. 「版本不匹配」工单占比 > 30% → 这是发布策略问题，收窄命名与 range，而不是增加版本线。

## 6. 开工前必须先核实的前提

- [ ] `[NEEDS VERIFICATION]` Waystones 是否发布与本仓库同级坐标的 Fabric 构件（`build.gradle` 里是 `waystones-neoforge`，命名暗示有，未实证）。
- [ ] `[NEEDS VERIFICATION]` Create: Enchantment Industry 是否有 Fabric 版（Create Fabric 是独立滞后移植，CEI 大概率没有）。若没有，Fabric 线上的内置表只剩少数几种流体。
- [ ] `[ASSUMPTION]` NeoForge 对 26.x 的构件版本号形式；首次移植前用真实构件核对。

这三条直接决定 P2 值不值得开；每条大约十分钟能查清。

## 7. 触发条件

出现下列任一情况再回来读本文并开工：

- mod 进入 1.0（接口与存档格式稳定）；
- 有整合包作者或服主明确要求某个版本/加载器；
- 当前主线的依赖（Waystones）跳到一个我们跟不上的大版本。
