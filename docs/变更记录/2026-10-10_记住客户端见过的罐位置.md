# 2026-10-10 记住客户端见过的罐位置（修"传回罐体"列表项仍灰）

## 改了什么

- 新增 `client/XppClientTankRegistry`：客户端按 `维度@位置` 记录**曾经加载过**的储罐位置（只记正向，
  `ConcurrentHashMap.newKeySet()`）。
- `block/entity/XpPaymentTankBlockEntity` 覆盖 `setLevel(Level)`：每次方块实体被创建（含区块加载）时登记位置。
- `client/XppClientRequirements`：`tankBelow` 改为返回 `boolean`——先查当前加载的方块实体，命中即登记；
  否则查客户端登记表。因此**目标石碑区块未加载时也能识别其下方的罐**。
- 诊断日志改为成对输出：`[client] no payment tank for this entry (from=..., target=...)` /
  `[client] payment tank known for this entry (from=..., target=...): allowing the teleport button (cost N XP)`。
- 重建并覆盖到测试实例（10-10 构建，见回复中的字节数/时间）。

## 为什么改

用户澄清症状是「**石碑中的选项是灰的，无法点击**」。先用 javap 与开发客户端做了硬验证：

- javap 用户实例的 `waystones-neoforge-1.21.1-21.1.45.jar`：`WaystoneList$WaystoneEntry` 确实调用
  `WaystonesAPI.resolveRequirements(...)`（偏移 62）并随后 `new WaystoneButton(...)`（偏移 78）；
  `WaystoneButton.<init>` 里 `WarpRequirement.canAfford(player)` 决定 `active`。
- 以 `-Dmixin.debug.export=true` 跑开发客户端，导出类
  `run/.mixin.out/class/net/blay09/mods/waystones/api/WaystonesAPI.class` 中含
  `handler$zzi000$waystone_xp_payment$xpp$paymentFromTank(...)` → **客户端 mixin 确实应用**。

既然钩子生效，灰色只能来自 `decorate` 返回了原需求。最可能的一种：**目标石碑所在区块在客户端没有加载**，
`level.getBlockEntity(waystone.getPos().below())` 必然为 null → 不包裹 → 该项永远灰。
服务端在传送时会加载目标区块，所以服务端一直是对的——问题纯在客户端"看不到"。

## 改动前后对比

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 站在罐体石碑处，列表里的去程项 | 可点（区块已加载） | 可点（不变） |
| **传回罐体石碑**（目标区块未加载） | 永远灰，无法点击 | 该罐只要本客户端曾加载过即**可点** |
| 首次遇到从未加载过的目标罐 | 灰 | 仍灰（客户端无从得知；服务端本可支付） |
| 排查 | 只能看单侧日志 | 正/负两条日志成对，`from=`/`target=` 带维度与坐标 |

## 根因分析与教训

1. **"服务端能做到"≠"客户端能判断"**：目标端付费在服务端已实现，但客户端预览需要判断"那个远处石碑下面有没有罐"，
   而未加载区块里根本没有方块实体。**把判定建立在只有一侧可见的信息上，就等于把功能绑在区块加载状态上。**
2. **缓存"稳定结构事实"是合理的**：罐位置不会变（除非被破坏），客户端曾见过即可长期使用；这与之前被否掉的
   "缓存易变的池值"完全不同——**可以缓存位置，不可以缓存数量**。
3. **验证手段要能证伪**：本轮先用 `javap`（注入点存在）+ mixin 导出（钩子真的应用）排除"mixin 没生效"，
   才把注意力收回到"客户端看不到罐"，而不是继续改匹配规则。
