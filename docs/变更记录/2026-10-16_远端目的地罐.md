## 2. 为什么改

机主 L3 实测（B6）：目的地罐满着，但目标区块未加载时入口是灰的。原因不是 bug 而是刻意设计——
`XppTeleportHandler` 在取不到方块实体时回退玩家自付，注释写明「Unloaded destination chunks land here on purpose」。
代价是「罐建在目的地、人从远处回来」这个最自然的用法实际用不上。

需求（机主 m01904 裁决）：默认允许，预算按设计执行，一轮做完。

## 3. 改动前后对比

| 场景 | 改动前 | 改动后 |
| --- | --- | --- |
| 远处目的地的入口 | 区块未加载 → 客户端无据 → 灰 | 服务端提示包给出池量 → 按真实池量点亮/置灰 |
| 服务端付款 | 未加载 → 回退玩家自付 | 配额内加载一次该区块 → 目的地罐优先付款，失败仍回退 |
| 打开菜单的开销 | 无 | 每 tick ≤1 个提示包、≤32 槽；**不加载任何区块** |
| 单次传送的加载开销 | 0 | 默认 ≤1 区块，同槽 5 s 内不重复 |
| 索引维护 | 无 | 罐内容变化/载入时写、方块移除时删；上限 4096 条 |

## 4. 备选方案与取舍

1. **传送完成后补扣（`WaystoneTeleportEvent$Post`）**：拒绝。传送已发生，扣不动只能追扣玩家，与 E-1/E-3 的账目原则冲突。
2. **客户端一律乐观（有罐就点亮）**：拒绝。退化为 C-2 记录的「按钮报价撒谎」，玩家白点一次。
3. **不做索引、只靠预加载**：拒绝。预览就没法给出真实池量，只能乐观或一律置灰。
4. **把索引放进 `DimensionDataStorage`（每维度一份）**：拒绝。跨维度目的地正是这个特性的目标场景，放主世界一份更好查；
   代价是自定义数据存储的整合包需要复核（已写入设计的已知限制）。

## 5. 根因分析

「目的地罐兜底依赖区块已加载」的根因是**读取路径只有一条**：`level.getBlockEntity(pos)`。它隐含两个假设——
（a）区块一定在内存里；（b）「读不到」等价于「不存在」。第（b）条正是 `UNKNOWN` 与 `NO_TANK` 必须分开的原因：
把两者合并，要么远处满罐永远灰（旧行为），要么不存在的罐被点亮（新的谎言）。
