# 2026-10-10 客户端可点选修复：mixin 装饰 Waystones 需求树

## 改了什么

- 新增客户端 mixin `mixin/WaystonesApiClientMixin`（配置 `waystone_xp_payment.mixins.json` 的 `client` 段）
  → 在 `WaystonesAPI.resolveRequirements(WaystoneTeleportContext)` 返回处，用
  `client/XppClientRequirements.decorate(...)` 装饰需求树
- 新增 `client/ClientFluidPaymentRequirement`（客户端可负担性镜像：罐先付、玩家补差、都不够则不可负担）
  与 `client/ClientFluidPaymentRenderer`（把图标/提示委托给被包裹需求的渲染器）
- `client/XppClientEvents` 在 `FMLClientSetupEvent` 注册该渲染器
- `XpPaymentTankBlockEntity`：新增 `getUpdateTag`/`getUpdatePacket` 同步（含服务端算好的 `XppPoolXp`）、
  `setChanged()` 时向客户端广播、`poolXpForClient()` 读取同步值
- `META-INF/neoforge.mods.toml` 增加 `[[mixins]] config = "waystone_xp_payment.mixins.json"`
- 重新构建并覆盖到测试实例（88,413 字节，2026-10-10 22:07:04）

## 为什么改

用户实测反馈：**罐里已经有经验流体（c:experience），但石碑界面里因为玩家自身经验不足，按钮是灰的，
点不了**——也就是根本走不到服务端，我们服务端的"罐先付"逻辑永远没机会执行。

根因（Waystones 源码，本地克隆 `D:\deepseek\_ref\Waystones`）：
- `client/gui/widget/WaystoneList.java:33-45`：客户端为每个目标石碑构建 context（`setFromWaystone(来源)`）
  并调用 `WaystonesAPI.resolveRequirements(context)` 解析需求树；
- `client/gui/widget/WaystoneButton.java:25`：`else if (!warpRequirement.canAfford(player) && !player.getAbilities().instabuild) active = false;`
  → 需求树是**客户端按配置**解析出来的（只含 XP 要求），与储罐无关，于是按钮被禁用。
- `InternalMethodsImpl.resolveRequirements` 是纯配置解析，没有任何事件钩子 → 只能从客户端侧介入。

## 改动前后对比

| | 改动前 | 改动后 |
|---|---|---|
| 玩家经验不足、罐里有经验 | 按钮灰色，点不了，服务端逻辑永不触发 | 装饰后的需求树判定"罐+玩家能负担"，按钮可点 |
| 服务端权威性 | — | 不变：装饰只在客户端生效（mixin 只在 `client` 段、且 `decorate` 对非客户端 context 直接返回原树），实际扣费仍由服务端 `FluidPaymentRequirement` 执行 |
| 图标/悬浮提示 | XP 图标显示禁用状态 | 委托原渲染器渲染，并按新的可负担性显示（另加一行"由下方储罐支付"） |
| 客户端如何知道罐里有多少 XP | 不知道（BE 不向客户端同步） | BE 的 `getUpdateTag` 带上服务端算好的 `XppPoolXp`；`setChanged()` 时广播 |

## 根因分析与教训

1. **"服务端已处理"不等于"功能可用"**：Waystones 的传送按钮是**客户端**按本地解析的需求树判定可用性的。
   任何依赖"服务端替换需求"的方案，都必须同时处理客户端预览，否则用户在第一道门就被挡住。
2. **客户端不能用本地速率表算池子价值**：数据包配方声明的流体只有服务端配方管理器知道，所以同步标签里
   直接带服务端算好的 `XppPoolXp`，客户端只读不推。
3. **软依靠内部 GUI 类要用最小侵入点**：`resolveRequirements` 是客户端所有预览（选择列表、物品栏按钮、
   快捷键处理）唯一的公共入口，注入这里一处即可覆盖全部入口；包裹式需求（wrapper + 渲染器委托）比"强行
   把按钮点亮"更不破坏其他需求（冷却/物品要求）的显示与判定。
4. **mixin 目标必须在你实际装的 jar 上核对**：`javap` 已确认 21.1.45 里存在
   `public static WarpRequirement WaystonesAPI.resolveRequirements(WaystoneTeleportContext)`；目标类属于模组
   （非 Minecraft 类，不做重映射），因此无需 refmap。
