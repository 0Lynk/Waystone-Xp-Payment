# 报价可见：一次传送到底付多少，只有一个答案

日期：2026-11-02
分支：`fix/pool-quote`

## 改了什么

**一、把「一次传送付多少」收口成 `payment/PoolQuote`**

新增 `src/main/java/com/olynk/waystonexppayment/payment/PoolQuote.java`（Minecraft-free record）：

```java
public record PoolQuote(int costXp, int poolXp, int xpFromTank, int xpFromPlayer, int tankMb, int missingXp,
                        int missingMb) {
    public static PoolQuote of(int costXp, int poolXp, XpRate rate, int playerXp);
    public boolean affordable();     // 罐 + 玩家够不够
    public boolean tankCoversAll();  // 罐自己付完，玩家不出钱
}
```

- `payment/PaymentSplit.compute` 改为委托它，结算仍用 `PaymentSplit` 这份「冻结的合同价」。
- `client/ClientFluidPaymentRequirement` 的 `canAfford`、`describeAffordability`、tooltip 全部走它。
- 新增 lang 键 `gui.waystone_xp_payment.tank_short`（中英各一条）：付不起时悬停显示「储罐只值 X 点经验，本次需要 Y 点（还差 Z mB）」。

**二、修 `sourcePackOf` 的路径拼接（真 bug）**

`event/XppGameEvents.java` 原来拼成 `namespace:data/recipe/<path>.json`，而资源管理器自己会加 `data/<namespace>/`，
于是永远查不到 → `via unknown:`、`packOrder` 全 0、设计文档 D6 承诺的「按包优先级覆盖」退化成按 recipeId 字典序。
改成 `namespace:recipe/<path>.json`。

**三、服务端「付不出去」的日志说清楚**

`event/XppTeleportHandler#payerAt` 原来对 `poolXp() <= 0` 打「declare the fluid…」，读起来像「这个流体没登记」。
现在打印实际 mB、流体描述、以及「1 XP 需要多少 mB」——1000 mB 的 10 XP/桶流体值 10 XP，不足 100 mB 时取整为 0，
这两种情况必须能从日志里分开。

**四、删死代码**：`recipe/XpFluidRecipe#matchesFluid` 已无调用方（全仓 grep 只有定义），删除及随之无用的 import。

## 为什么改

机主实测：Ender IO / Create 管道与排液口都能灌入灌出四种便宜流体，但传送条目是灰的。
取证后的结论是**没有身份 bug，是价格**：这四种 = 10 XP/桶，1000 mB 只值 10 XP，而一次远距离传送要 27 XP
（日志：`pool 10 XP (cost 27 XP)`、`greyed out: tank 10 of 10 XP, player 17 of 0 XP, cost 27 XP`，两秒后玩家凑够 17 点即自动变亮）。
旧版 `mbPerXp = 1` 时任何登记流体都值 1000 XP/桶，这套差异从未暴露。

真正的问题是**系统知道付不起，却只让按钮变灰**：罐界面显示 1000 mB，传送提示只说「需要 27 点经验」，
两条信息凑不出「这罐只值 10 点」这个结论。所以这一轮不改费率，改**可见性**：一份报价，四处复用。

## 改动前后对比

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 罐里 1000 mB 便宜流体，玩家 0 XP，票价 27 | 条目灰，提示只说「需要 27 点经验」 | 条目灰，提示追加「储罐只值 10 点经验，本次需要 27 点（还差 1700 mB）」 |
| 同一罐，玩家 17 XP | 亮 | 亮（10 + 17 = 27） |
| 「付多少」的计算 | `PaymentSplit`、客户端 `canAfford`、`describeAffordability` 各算一遍 | 只有 `PoolQuote.of` 算 |
| 数据包归属 | 恒 `unknown`，包优先级失效 | 正确读到 `sourcePackId` |
| 罐里 <100 mB 的便宜流体 | 日志说「declare the fluid…」，像是没登记 | 日志给出实际 mB 与「1 XP 需要多少 mB」 |

## 备选方案

- **a. 抬高这四种流体的费率（10 → 40）**：一桶就能付一次远距离传送，但等于凭空放大支付能力，与「按实测官方兑换定价」冲突，机主已否决。
- **b. 入罐时拒收「满罐也付不起一次传送」的流体**：能消除「能灌不能付」的错觉，但判据依赖容量与票价配置，改配置就会翻转合法性，把经济判断塞进 capability 谓词。
- **c. 只改界面文案**：最省，但计算仍散在五处，下一次改单位或改取整还会分叉。

选 **c 的意图 + 结构收口**：不改经济、不改协议，把报价收成一个对象，再把缺口的数字显示出来。

## 意外点

1. `PoolQuote` 一旦算错，五处会一起错——所以它必须是纯函数并单独测试（新增 8 例），而不是散在界面里的临时算术。
2. `missingXp` 定义为「玩家还需自掏多少 XP」，而不是「罐还差多少 XP」：玩家手上有钱时这两者不同，tooltip 要的是前者对应的 mB。
3. `PackType.SERVER_DATA.getDirectory()` 那一行的拼接错误在日志里只表现为 `via unknown:`，不会抛异常，也不影响费率生效——只能靠读日志发现。
