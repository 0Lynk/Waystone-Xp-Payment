# 访问界面第三轮改造：选中 / 右键菜单 / 队伍成员

日期：2026-10-11
依据：`docs/界面规格-第三轮.md`（§2–§8），并按任务书的三条取舍覆盖规格冲突处。

## 改了什么

### 协议（新增一份，改一份）

- 新增 `net/XppMembersPayload.java`：服务端 → 客户端的队伍成员包，字段 `pos / teamId / teamLabel / status / requestId / members[]`。
- 新增 `net/XppMembersStatus.java`：状态字节（0 OK / 1 NO_TEAM_MOD / 2 UNKNOWN_TEAM / 3 NOT_OWNER）与面板态（LOADING / OK / EMPTY / NO_TEAM_MOD / UNKNOWN_TEAM / DENIED / TIMEOUT）的纯映射，含文案键。
- `net/XppAccessPayload.java`：`Action` 增 `REQUEST_MEMBERS`；record 增 `long requestId` 分量，编解码各加一次 `writeLong`。
- `net/XppServerHandler.java`：`REQUEST_MEMBERS` 在 `apply` 之前分流；走同一道 owner gate；**被拒时除了储罐快照，还会回发 `status=NOT_OWNER` 的成员包**。
- `event/XppModEvents.java`：`registrar("1")` → `registrar("2")`，并注册成员包。

### 反射

- `auth/TeamResolver.java`：新增 `MemberInfo`、`MembersResult` 与 `default MembersResult membersOf(UUID)`（默认回答 NO_TEAM_MOD）。
- `auth/FtbTeamsResolver.java`：反射 `Team.getMembers()`、`Team.getOnlineMembers()`、`TeamManager.getTeamByID(UUID)`；在线名取 `ServerPlayer.getGameProfile().getName()`，离线名走 `MinecraftServer.getProfileCache()` → `GameProfileCache.get(UUID)`，取不到退化为 UUID 前 8 位。

### 客户端

- 新增 `client/ContextMenuLayout.java`：菜单宽度与翻转/夹取坐标的纯计算。
- 新增 `client/PendingRequest.java`：在途请求与「回包快照是否证明它生效」的纯判定。
- `client/AccessButton.java`：支持一个替代文案绘制的字形（成员面板返回控件的 `<`），并把 `getMessage()` 保留给无障碍朗读。
- `client/XppClientState.java`：新增 `acceptMembers`。
- `client/XpPaymentTankScreen.java`：重写交互层（五态状态机、右键菜单、单选、成员面板、状态条、pending 脉动）。
- 两个语言文件按 §7 重写为 46 键。

### 测试

- 新增 `ContextMenuLayoutTest`（12 个）、`PendingRequestTest`（12 个）、`XppMembersStatusTest`（6 个）。

## 为什么改

原实现的交互把「选中」和「执行」压在同一个左键上：候选行左键即发包、名单行的 × 热区左键即删除。玩家因此看不到任何中间反馈，也无法在动手前确认自己点中的是哪一行。本轮把两个手势拆开——左键只选中、右键才展开菜单——并给每个请求加上「发送中 / 已生效 / 被拒 / 无响应」的可见结果。

新增协议是被需求形态逼出来的：队伍成员只存在于服务端（FTB Teams 的 `Team.getMembers()`），客户端既没有队伍模组也可能没有该队伍的任何缓存，因此「查看队伍」必须是一次往返，且必须有一个能区分「队伍没人」与「服务端没有队伍模组」的状态字节。

## 改动前后对比

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 左键候选行 | 立即发 ADD_* 包 | 只选中；添加改为右键菜单项，或候选模式下对键盘高亮行按 ENTER |
| 左键名单行 `x≥229` | 立即发 REMOVE_* 包 | 打开该行菜单（同一像素区间，改画 `···`） |
| 右键 | 无 | 展开菜单：添加 / 删除 / 查看（不可用项置灰，恒画三项） |
| ESC | 两段：退候选 → 关界面 | 三段：关菜单 → 退候选 / 退成员面板 → 关界面 |
| 反馈 | 无 | 状态条右段四态 + 停留时长；行尾三点脉动；pending 行不画菜单槽 |
| 只读态 | 行区中央一句「只读」 | 照常显示并可选中列表；只读说明移到状态条右段常驻 |
| 队伍成员 | 不可见 | 菜单「查看」进入成员面板（标题 / 返回控件 / 成员行 / 状态点 / 五态文案） |

## 根因分析

1. **「点击无反馈」的根因是动作没有中间态**。旧代码里一次左键 = 一次发包 = 一次快照重绘，玩家能看到的只有结果，且结果常常与操作前无差别（例如重复添加）。改为「选中 → 菜单 → 单项动作 → 在途 / 结果」之后，每一步都有可见状态，重复添加也在菜单里被直接置灰、根本不下发。
2. **删除热区紧贴行体是危险的默认值**。`DELETE_X=229` 与行体只差一次鼠标移动，误触即丢数据。同一块像素改作菜单入口后，破坏性动作需要「右键 → 选中删除项 → 左键」三次明确手势。
3. **成员面板必须由服务端驱动**，这是数据来源决定的，不是设计偏好：客户端侧的 FTB Teams 可能不存在。
4. **`requestId` 是必需的**，否则「关掉再开」「超时重试」会让先发的回包落在后一次请求上，加载态会在错误的时间结束。

## 复核修正（同日补充）

交付后由主会话逐处复核代码与规格，发现并修掉两处：

1. **成员行的选中洗色被行底盖住**：`drawMemberRow()` 原先先画 `COLOR_PLAYER & 0x22FFFFFF`（8% 洗色）再画不透明行底 `COLOR_ROW_BG_PLAYER`，洗色等于没画。已改为与 `drawRow()` 同序（行底 → 洗色 → 左侧强调条），成员行的选中反馈与名单行一致（选中框此前已正常）。
2. **容器描边（规格 §1 P0-6）此前未落地**：`renderBg()` 现在补上 `FRAME_LEFT/TOP/RIGHT/BOTTOM = 5/76/251/238` 的 1px `0xFF3A3A3A` 边框与 `0x14000000` 底，把输入框、表头、行区、状态条框成一块；画在 `renderBg()` 而不是 `render()`，因为行填充是半透明的，这一层必须在它们下面。输入框保留自己的边框（焦点/错误态靠它表达）。

复核通过的部分（逐处读过代码，非只看汇报）：

- 左键只选中、右键展开菜单、菜单外点击被吞掉、菜单内点禁用项不关闭；`⋯` 换成三个 `·`（U+00B7，1.21.1 字体图集里 U+22EF 不存在）。
- 输入框点击走 `setFocused(searchBox)`（界面级指针）+ `setCursorPosition(len)`；ESC 三段式；`menuOpen` 时 `renderTooltip`/`renderRowTooltip` 整体短路。
- `menuItemEnabled`：添加仅在「候选中 + 有 UUID + 未在名单 + 无在途请求」时可用；删除仅在名单行可用；查看仅在有 UUID 的队伍行可用（legacy 队伍行禁用，因为请求按 id 寻址）。
- `rowIndexAt` 的显式下界修掉了「行区上沿再上一像素点中第 0 行」的截断 bug。
- 语言键 en/zh 各 46，双向差集为空、无空值；`:test` 54 例全绿。

## 自定夺（与规格不一致或规格未写）

- **规格 §3 的 `⋯`（U+22EF）改为三个 `·`（U+00B7）**：前者不在原版字体图集中，等高考据覆盖后者。
- **规格 §3「PICKER·玩家行『添加』恒可用」与 §6「幂等例外」冲突**：以 §6 为准——已在名单则菜单置灰、根本不下发。
- **规格 §3「legacy 队伍行『查看』可用」不成立**：成员请求按 `UUID teamId` 寻址，legacy 队伍行没有 id，机制上不可表达（§5.6 也写明不发请求）。
- **`XppAccessPayload` 增 `requestId`**：规格只写了「Action 增 REQUEST_MEMBERS」，没规定回程如何配对；`requestId` 是回包唯一的配对通道。
- **`TeamResolver.membersOf` 返回 `MembersResult(status, members)`**：空列表无法区分「队伍没人 / 没有队伍模组 / 队伍已解散」三种文案。
- **多目标请求引入 `INCOMPLETE`**：「+ 添加我的队伍」一次点发 N 个包、服务端每包回一次快照，第一个回包不是整请求的答案，不能把它读成「已生效」。
- **规格 §1 P1-8「所有者移进状态条」未采纳**：所有者仍画在表头右端（`drawHeader`）。状态条右段已经被「发送中/已生效/被拒/超时/只读」占用，把所有者塞进左段会和「模式 · 条目」挤在一行；表头一行放「访问列表 (N)」+「所有者：X」目前不冲突。
- **成员行的 `✔`/脉动点不在同一列**：`✔` 固定在标签右端（≤199），脉动点在 209/214/219，两块绿色相邻但同屏不同形（脉动点在动），保留。
