# 等待答案期间不冒充可付（第 11 轮）

日期：2026-10-29
分支：`fix/pending-answer-gate`
相关：`client/XppTankHints.java`、`client/ClientFluidPaymentRequirement.java`、`event/XppTeleportHandler.java`

## 什么问题逼出了这次改动

机主现场复测（泵持续抽 A 罐，残余约 40 mB）：从 A 传送到远端 B 后 A 的区块停止加载，立刻在 B 打开
传送列表，「传送到 A」这一行**先亮一下、随即变灰**；在亮着的那一两帧里点击，大多数时候被服务端以
「付不起」拒绝。

两个独立的问题叠在一起：

1. **「问题还在飞」被当成了「可以付」。** 列表是在答案回来之前构建的：`tankBelow` 对未加载的槽位
   调用 `XppTankHints.request()` 之后立刻 `selectPayerSlot`，靠 `XppClientTankRegistry` 记得的槽位
   交出一个 `TankRef(loaded=null)`；`payerAt` 见 `hint == null` 按设计**宽松放行**，于是条目被包装；
   `canAfford` 里 `knownPoolXp()` 返回 `null` 被读成「没有信息 ⇒ 可以付」⇒ 按钮亮。1–3 tick 后答案
   落地（40 mB ≈ 2 XP < 27 XP）⇒ 按钮灭。亮的那 1–3 tick 里点下去必然失败。
2. **信任窗与列表构建口径不一致。** `TRUSTED_MILLIS` 是 30 s，而列表构建用的是
   `LIST_OPEN_MAX_AGE_MILLIS = 5 s`。界面一直开着时，答案只会越用越旧：5 s 之后本该重问，实际要等到
   30 s 才触发 `refreshIfStale`，中间 25 s 靠一个过期读数决定按钮。

同一轮还顺手对齐了一处服务端与客户端相反的口径（见「改了什么」的第 4 点）：罐里装着**不被承认的
流体**时（`poolXp() <= 0` 但罐非空），服务端只打一条 warn 就把它当付款方，于是另一端有罐也不会被考虑；
客户端 `paysFrom` 早就不认它。结果就是「客户端说目的地罐付，实际玩家全付」。

## 改了什么

**改动前后对比**

| 位置 | 改前 | 改后 |
|------|------|------|
| `XppTankHints.request()` | 入队即完事 | 该槽**没有答案**时同时记进 `IN_FLIGHT`；`accept()` 收到答案时清除 |
| `XppTankHints` 新增 | — | `awaitingAnswer(dimension, pos)` + 纯函数 `stillWaiting(askedAt, now)`，等待上限 `ANSWER_WAIT_MILLIS = 1_000L` |
| `XppTankHints.TRUSTED_MILLIS` | `30_000L` | `5_000L`，并删除 `LIST_OPEN_MAX_AGE_MILLIS`，`dueForListOpen` 复用同一个常量 |
| `ClientFluidPaymentRequirement.canAfford` | 池量读不到 ⇒ 只比 residual ⇒ 亮 | 池量读不到且**问题在飞** ⇒ 先灰；1 s 内仍无答案则回落放行 |
| `ClientFluidPaymentRequirement.describeAffordability` | 只有 `no pool reading here` | 增加 `waiting for the first reading of that tank` |
| `XppTeleportHandler.payerAt` | `poolXp() <= 0` 只 warn，仍返回 `Payer` | warn 之后 `return null`，让另一端的罐有机会，与客户端 `paysFrom` 一致 |

`canAfford` 现在是两个「不该亮」的理由取并集，再统一过一个创造模式豁免：

```java
boolean unresolved = poolXp == null && awaitingReading();
boolean tankShort = poolXp != null
        && !PaymentSplit.compute(costXp, poolXp, knownMbPerXp(), player.totalExperience).affordable();
if ((unresolved || tankShort) && !skipsPayment(player)) {
    return false;
}
```

## 考虑过哪些备选方案

- **a. 每次渲染都重选付款方**（`XppClientRequirements` 把两个 `TankRef` 都存进 requirement，每帧按
  `payerAt` 规则重挑）。收益是「两端都有罐」时按钮更准：源罐抽干后还能自动改口说目的地罐付。代价是
  把「按钮每一帧都可能换付款方」变成新语义，hover 文案、日志、`describeAffordability` 都要跟着改，
  且它解决的是「灰得太早」，不是本次报告的「亮了又灭」。**本轮不做，登记为 P1。**
- **b. 在飞时继续宽松放行**（即现状）。这正是要修的行为，排除。
- **c. 开列表前一 tick 预取**（在 `WaystoneSelectionScreen` 打开时先发一轮查询）。只能缩短等待窗口，
  不能消除「窗口内靠猜」，而且要把请求提前到 GUI 构造之前，等于把时机关心藏进另一处。排除。
- **d. 全局「过期读数只准拒绝、不准放行」**。这会让一个满罐的远端条目在读数过期后灰掉，等于把第 9 轮
  修掉的「满罐永远灰」请回来。排除，只保留「答案不会因为过期而被丢弃」这条既有规则。

取舍：选择「未知时先灰、有答案再定」，因为**亮着点不了**比**晚 100 ms 才亮**更伤：前者消耗玩家的
信任，后者只多等一两个 tick。等待窗口设 1 s，是为了让一个不回话的服务端不会把条目永久锁死。

## 有什么意外点

1. 「未知槽位不包装」与「已加载空罐仍包装」是两条不同的路径：第 9 轮的 `readableTank` 兜底只管后者
   （罐就在本地、只是空的），本轮的在飞判定管前者（槽位是记得的、罐在别处）。两者不能合并成一条规则，
   否则会把「从来没有答案」重新引回「当成空」。
2. `refreshIfStale` 触发的重问**不**写 `IN_FLIGHT`：那时我们有旧答案，正在用的就是它，不应该因为「发了
   一个新问题」就把按钮临时变灰（否则每次重问都会闪一下）。
3. `IN_FLIGHT` 里没被回答的键不会自然消失，只靠 `ANSWER_WAIT_MILLIS` 判定过期；`clear()` 会一起清掉，
   一个会话里最多是打开过的槽位数，可以接受。TCP 下答案不会真的丢，真出现也只影响 1 s。

## 验证

- `.\gradlew.bat test --offline`：**22 suites / 140 tests / 0 failures**（137 → 140，新增 3 例）。
- 负向验证 ①：`ANSWER_WAIT_MILLIS` 改 `0L` ⇒ `aQuestionInFlightIsWaitedFor`（`:68`）与
  `waitingEndsWhenTheAnswerIsOverdue`（`:73`）变红，还原后全绿。
- 负向验证 ②：`TRUSTED_MILLIS` 改回 `30_000L` ⇒ `XppTankHintsTest` 挂 4 例
  （`:32`/`:42`/`:48`/`:53`），还原后全绿。
- **未覆盖**：`awaitingAnswer()` 的真实入队/清队路径需要客户端世界；`XppTeleportHandler.payerAt` 的
  `poolXp() <= 0` 分支需要 `ServerLevel` 与方块实体。两者都只做了代码复核，没有单测——如实记在这里。

## 待实机验证（机主侧）

1. 复现原场景（泵抽 A 罐到 ~40 mB，A→B 后立刻开列表）：**「传送到 A」应该一开始就是灰的**，不再先亮后灭。
2. 把 A 的罐补到足够（≥27 XP）后**重开列表**：条目应在 1–2 tick 内变亮（等待窗口的代价）。
3. 界面一直开着：用泵把某个远端罐抽干/灌满，按钮应在 ~1 s 内跟随（信任窗从 30 s 收到 5 s）。
4. 两端都有罐、且只有一端装的是不被承认的流体：预览与服务端都应跳过那个罐，改用另一端（
   `[client] ...` 与 `Tank at ... cannot pay` 两条日志应能对上）。
