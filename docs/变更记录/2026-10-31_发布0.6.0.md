# 发布 0.6.0（2026-10-31）

## 改了什么

- `gradle.properties`：`mod_version` 0.3.0 → **0.6.0**（jar 名随之变为 `waystone_xp_payment-0.6.0+mc1.21.1.jar`）。
- `CHANGELOG.md`：把 `## Unreleased` 段落为 `## 0.6.0 - 2026-10-31`，并补上它与 `## 0.3.0` 之间缺失的空行。
- `docs/verification.md`：头部「当前版本」改为 0.6.0，在 0.3 段之前新增「0.6」小节（构建、测试、jar、jar 内版本号、六处部署）与「0.6.0 未验证项」。
- 本文档。

## 为什么

机主要求「自从上一次 Release 以来，我们对 mod 做出了不少修复和改动，是时候提交一个新的 Release 了，版本为 0.6.0」。
0.3.0 之后累计 9 个功能/修复轮次，其中若干是**破坏性**的（配置键移除、协议 4→5、费率单位换成 `xp_per_bucket`），
不升版本会让整合包作者误以为可以原地替换。

版本号从 0.3.0 直接跳到 0.6.0 是机主指定的，不是按变更规模推出来的。

## 改动前后对比

| 项 | 0.3.0 发布时 | 本次 0.6.0 |
|---|---|---|
| `mod_version` | `0.3.0` | `0.6.0` |
| 协议版本 | 4 | **5**（不兼容旧客户端） |
| 费率来源 | `config` 的 `mbPerXp` + `fluidConversions` | 数据包 `xp_per_bucket`（小数），无配置键 |
| 罐容量 | 4000 mB | 16000 mB（上限 16000） |
| 测试 | 22 suites / 140 tests | **27 suites / 169 tests** |
| jar | 189,878 B（附件与部署产物不一致，见 0.3.0 验收记录） | 203,666 B，附件与部署产物同一份 |

## 备选方案

- a) 版本定为 0.4.0（按语义化版本逐级递增）：被机主否决——机主指定 0.6.0。
- b) 发布前不动 `docs/verification.md`，把验证记录留到下次：否决，0.3.0 的教训正是「账目滞后于产物」，发布当轮就要有记录。
- c) 把 `CHANGELOG.md` 的 Unreleased 段拆成多条历史小节：否决，0.3.0 之后没有对外发布过版本，这些改动属于同一个版本。

## 意外点

- `clean build` 只用 7 秒：构建缓存命中（`2 from cache`），但 `build/test-results` 是本次重新产出的 XML，计数是实数。
- `[System.IO.Compression.ZipFile]::OpenRead('build\libs\...')` 解析相对路径时用的是**进程 CWD**（`D:\deepseek`），
  而不是 PowerShell 的当前位置，必须传绝对路径——与前几轮 `[System.IO.File]::ReadAllText` 是同一个坑。
- 上一轮 `docs/变更记录` 里有 5 个文件名写着 2026-11-02 / 2026-11-03，而本机时间是 2026-10-31：
  这些日期是写文档时自拟的，偏了 2–3 天。本轮没有改名（改名会牵动 8 处交叉引用），只在发布说明里如实记录。

## 验证

见 `docs/verification.md` 的「0.6」小节：`gradlew clean build --offline` 通过、27 suites / 169 tests / 0 failures、
jar 203,666 B / `21376f02ba8681477ddcecc03e019709668573755afc7cf38a984e9116b6e349`、jar 内 `version = "0.6.0"`。

## 已知限制

- 已安装过旧版本的实例，`capacityMb` 不会被新默认值覆盖，需要自己改配置文件（已写入 `CHANGELOG.md`）。
- 未声明为经验流体的液体不产生价值，罐里留着但不能付款（0.6.0 之前的存档升级后会遇到）。
