# 发布 0.6.1（2026-10-31）

## 改了什么

| 文件 | 改动 |
|---|---|
| `gradle.properties:13` | `mod_version` 0.6.0 → **0.6.1**（jar 名随之变为 `waystone_xp_payment-0.6.1+mc1.21.1.jar`） |
| `CHANGELOG.md` | `## Unreleased` 落为 `## 0.6.1 - 2026-10-31`，按 Fixed / Changed / Notes 三节重排：两个占位汇率是**修正**，提示文案与第二行统一是**改动**；新增 Notes 说明「不需要改数据包或配置」「被删掉的差额提示」 |
| `docs/verification.md` | 头部「Current release」改 0.6.1；在 0.6 段之前插入 `## 0.6.1` 小节（构建、测试、两次反向验证、jar 与版本号、六处部署、冒烟）与 `### Not verified for 0.6.1` |
| 本文件 | 发布记录 |

## 为什么发这一版

机主 2026-10-31：「推送新的Release，0.6.1，写好更新日志」。

从 0.6.0 的 tag（`990da9be`）到现在，main 上多了两个提交：PR #66（提示文案去掉「下方」、三条第二行合并成一句）
与 PR #67（超越维度、精妙存储的汇率从占位值 1000 改为实测的 10）。前者改变玩家看到的文字，后者改变玩家实际付出的量
——尤其是后者，旧值让这两种流体**少付 99%**，越早替换越好。

## 备选方案

| 方案 | 取舍 |
|---|---|
| a. 直接发 0.6.1，更新日志只写在 Release 页面 | 仓库里没有对应段落，`git diff v0.6.0..v0.6.1` 的人看不到解释；0.6.0 已经确立了「CHANGELOG 是正式记录」的先例 |
| b. 跳 0.7.0（提示文案形状变了） | 没有 API、数据包契约、存档格式的变化，汇率修正属数据修正，补丁号更诚实 |
| c. **按 0.6.0 的顺序**：先合并、再从合并后的 main 构建一次、同一份既做附件又做部署（采纳） | 多一次构建，换来「附件与部署产物逐字节一致」；这正是 0.3.0 踩过的坑，0.6.0 起已固定为流程 |

## 意外点

1. `docs/verification.md` 还写着「Current release: 0.6.0」并钉着 0.6.0 的哈希，不改就会与 Release 页面自相矛盾。
2. `build\libs` 里留着上一版的 0.6.0 jar 与新 jar 并列，随手复制就会把旧包发出去——发布前已删除，只留 0.6.1。
3. 版本号只改 `gradle.properties` 一处即可，jar 内的 `version` 由构建期展开，改完必须回读 jar 复核（见验证表）。

## 验证

见 `docs/verification.md` 的 0.6.1 小节：`gradlew build --offline` 通过、27 suites / 167 tests / 0 failures、
jar 203,427 B / 140 个 zip 条目、jar 内 `version = "0.6.1"`、六处部署同一 sha256、`gradlew runServer` 冒烟干净停机、
GitHub Release 附件与部署产物逐字节一致。

## 已知限制

- 反向兑换（流体抽回玩家经验）仍未被测，内置表的依据仍是「造出这份流体要花多少经验」。
