# 设计：经验流体费率改由数据包决定

> 状态：已定稿，等待实现（2026-10-30）
> 取代：`docs/设计-远程目的地罐.md` §2 中「费率来自配置」的全部描述

## 1. 背景

旧实现里「哪种流体算经验、多少 mB 值 1 XP」有两个来源：配置项 `fluidConversions`（`<id>=<mB per XP>` 字符串列表）+ 数据包配方 `waystone_xp_payment:xp_fluid`。两者共用一条字符串通道，后加入的配方条目直接覆盖配置条目，于是：

- README 写的「配置优先」与实现相反；
- `/reload config` 走 `FluidRates.rebuildFromConfig()`，只读配置，配方声明的流体整张表消失，满罐瞬间按 0 值计价；
- 单位是「mB / 1 XP」的整数，写不出 1 mB 值 2 XP 这种更浓的流体。

## 2. 决定

| 编号 | 决定 | 理由 |
|---|---|---|
| D1 | 费率**只**来自数据包，配置不再登记流体、不再设汇率 | 一个概念只有一个写者，覆盖语义才可能确定 |
| D2 | 单位改为 `xp_per_bucket`（每桶 1000 mB 值多少 XP），允许小数 | 「更浓的流体」能被表达：`0.5` = 2 mB 值 1 XP，`2.0` = 1 mB 值 2 XP |
| D3 | 内部一律整数毫 XP 运算：`milliXpPerBucket`（1000 = 1.0 XP/桶） | 钱不能走浮点；`0.5` 精确可表示 |
| D4 | 只认精确流体 id；still/flowing 用 **流体对象** 归一（`FluidIds.canonical` → `FlowingFluid#getSource`），命名规则只作非 `FlowingFluid` 的兜底 | 标签与 id 的优先级冲突无法用一句话说清，直接删掉标签这一维；而 id 字符串猜不出孪生（三种命名派别并存），只有流体对象知道自己是谁 |
| D5 | 删除「名字像经验就当作经验」的启发式 | 它是猜，猜错就是白送或白扣 |
| D6 | 覆盖按包优先级：同一个配方 id 由后面的包覆盖前面；不同 id 声明同一流体时，包位置靠后者赢，同包内按配方 id 字典序靠后者赢 | 与原版数据包语义一致，且完全可由 API 决定，不需要实机试 |
| D7 | `xp_per_bucket: 0` 表示注销该流体 | 让整合包能「取消」内置表里的条目，而不必覆盖整张表 |
| D8 | 内置一份默认数据包（`data/waystone_xp_payment/recipe/builtin/*.json`），覆盖主流经验流体 | 玩家装完就该能用，不该被要求先写数据包 |
| D9 | 协议版本 4 → 5；旧 NBT 按「未知」读，不做猜测换算 | 单位语义变了，混读就是错账 |
| D10 | 存档里存的是派生值（XP），迁移风险接受；mod 仍是测试版本，只要不崩存档 | 用户 2026-10-30 决定 |

## 3. 覆盖顺序如何确定（D6 的可实现性）

反编译 1.21.1 映射 jar 确认存在三个 API：

- `Resource.sourcePackId()` / `Resource.knownPackInfo()` → 这个配方文件来自哪个包（`KnownPack` 还带 `isVanilla()`）；
- `ResourceManager.getResourceStack(ResourceLocation)` → 同一路径在所有包里的资源栈，按优先级排列；
- `PackRepository.getSelectedPacks()` → 当前启用的包顺序。

因此排序键可以是 `(包位置, 配方 id)`，不需要实机实验。`getSelectedPacks()` 的返回顺序是否等价于「从低到高」仍需在实现时用一条断言固化（`[NEEDS VERIFICATION]`，实现完成后转为单测）。

## 4. 未登记流体的处理

- 新流体：罐体不接受（与旧行为一致），因为没有费率就不会有 `xpValue`。
- 旧存档里已有、但新表里没有登记的流体：**加载该罐时清空并记一条日志**。前提是费率表已经装载过（`declaredCount() > 0`），否则数据包未就绪时会把合法流体误清。

## 5. 与客户端的关系

客户端不持有费率表。它只知道服务端通过 hint 告诉它的 `xp_per_bucket`；所有金额判断以服务端为准，客户端只负责置灰与提示。

## 6. 影响面

`mbPerXp` 语义出现在 16 个文件：`fluid/FluidRateTable`、`fluid/FluidRates`、`recipe/XpFluidRecipe(Serializer)`、`payment/{PaymentSplit,PaymentSettlement,FluidPaymentRequirement}`、`block/entity/XpPaymentTankBlockEntity`、`data/TankPoolIndex`、`net/{XppStatePayload,XppTankHintPayload,XppServerHandler}`、`client/{ClientFluidPaymentRequirement,XpPaymentTankScreen}`、`config/{XppConfig,XppSettings}`、`event/XppGameEvents`。

## 7. 不做什么

- 不做“按名字猜流体”的推算（同 mod 同一流体只有一个真相）；但 **静止/流动是同一个物质的两种形态，不是两个真相**，所以按流体对象归一到静止形态是允许且必须的（见 D4）；
- 不做「入罐即锁定价值」；
- 不保留 `mb_per_xp` 的兼容读取（老数据包写该字段 → 该条失效并报错，避免半懂不懂的配置静默生效）。
