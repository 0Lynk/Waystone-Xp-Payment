# 客户端预览与置灰代码的可读性整改（/revise Pass 2）

日期：2026-10-24
范围：`client/PaymentGreyState.java`、`client/ClientFluidPaymentRequirement.java`、
`client/XppClientRequirements.java`、`client/XppClientRequirementsTest.java`

## 改了什么

纯可读性重构，**行为不变**，四个文件共 +28/−19。

### 1. `PaymentGreyState.nextActive` 去掉无解释价值的临时变量

```java
if (!affordable) {
    boolean wasClickable = activeNow;      // 删
    greyedByPayment = true;
    return wasClickable ? Boolean.FALSE : null;
}
```

`wasClickable` 只是 `activeNow` 的改名，没有提供调用点读不出来的信息；三目运算符里直接用 `activeNow`
更短，也不改变阅读顺序（先记「这灰是我们的」，再决定要不要真的写回）。

### 2. `ClientFluidPaymentRequirement.canAfford` 合并重复的创造模式判断

改前有两条各自 `return residual == null || residual.canAfford(player);` 的路径：创造模式早退一条，
常规流程结尾一条。改后把创造模式收成一个谓词，只在「罐里的钱不够」这一支上判断：

```java
Integer poolXp = knownPoolXp();
boolean tankShort = poolXp != null
        && !PaymentSplit.compute(costXp, poolXp, knownMbPerXp(), player.totalExperience).affordable();
if (tankShort && !skipsPayment(player)) {
    return false;
}
return residual == null || residual.canAfford(player);
```

`skipsPayment` 带 javadoc 说明为什么跟 `skipPaymentInCreative` 配置走而不是只看 `instabuild`：服务端把 skip
关掉时仍然收费，客户端此时无条件放行就是「亮着但被拒」，所以两侧必须同一个开关。

### 3. `XppClientRequirements.decorate` 里两处结构收紧

- 自目标判定的两个 UUID 各自用一个 `Optional.map(...).orElse(null)` 取出（原来靠一个私有 `waystoneUid`
  包装，重构后只剩一处调用点，包装不再省任何字，删掉）；
- 付款方解析里 `payer == null` 原来判了两次（一次在三目里，一次在 `if` 里），改成先取一次源端，
  为空才去取目的端：

```java
TankRef payer = payerAt(sourceTank);
TankRef targetTank = null;
if (payer == null) {
    targetTank = tankBelow(level, context.getTargetWaystone());
    payer = payerAt(targetTank);
}
```

### 4. `XppClientRequirementsTest` 的类 javadoc 补上新增的一组测试

原文只写「哪一格的罐在付款」，而 Pass 1 加的三例（自目标）不在这个描述里。改为两组各一段：
槽位选择守什么、自目标守什么。

## 为什么改

Pass 1 已把误伤修完（`isSameWaystone` 早退、`skipsPayment` 跟配置走），Pass 2 只处理当时推迟的
可读性问题：临时变量、重复早退、双重 `== null` 判断、与代码不同步的测试类 javadoc。

## 考虑过的备选方案

- **a. 不动 `decorate` 的结构**：保留了「`targetTank` 用三目赋值、下一行再判一次 `payer == null`」的写法。
  拒掉是因为同一条件判两次会让读者以为两次之间有什么发生了。
- **b. 把 `describeAffordability` 的字符串拼接换成 `String.format`**：拒掉。项目里 `String.format` /
  `.formatted(` 零使用，`" + var` 拼接 54 处；为一条日志消息引入格式串家族反而破坏一致性。
- **c. 把 `nextActive` 的三态 `Boolean` 换成枚举**：拒掉。调用点只需要「要不要写回、写什么」两件事，
  枚举会多一层名字与 switch。
- **d. 顺手给 G-4（阈值反复横跳时每次翻转刷一行 INFO）加节流**：拒掉。那是新行为，不属于 revise 范围，
  已在 `docs/问题修复清单.md` 记为保留项。

## 意外点

- 删掉 `waystoneUid` 包装后，`@Nullable` 注解也跟着无处安放；编译器没有提示，是搜引用时发现的。
- `targetTank` 现在初始化为 `null` 再在分支里赋值，三目改成 if 后局部变量的「可能为 null」更直白，
  也不影响下面日志里 `describeTank(targetTank)` 的 null 安全。
