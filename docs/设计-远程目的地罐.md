# 设计：远端目的地储罐

> 状态：已实现（本轮 PR），待实机验证
> 关联问题：`docs/问题修复清单.md` 的 N-7（原「目的地罐兜底依赖目标区块已加载」）

## 1. 问题

传送的付款罐按「源纪念碑下方的罐 → 目的地纪念碑下方的罐 → 玩家自身」的顺序选取（`event/XppTeleportHandler.java`）。
目的地那一端原本有一条刻意写下的限制：目标区块没加载时，服务端读不到方块实体，于是**回退到玩家自己付**——
宁可让玩家掏 XP，也不猜那个罐里有什么。本轮把这条限制换成了「先按预算加载一次再判断」（`tankAt`），
语义从「不猜」变成「用一次有上限的加载去查证」。

于是出现了实机反馈的现象（机主 L3 测试 B6）：玩家站在远处、目的地罐满着 4 桶经验，但目的地按钮是灰的——
因为客户端也同样看不到那个罐，只能按「玩家 XP 够不够」来点亮。

这条限制本身是安全的（不猜、不偷跑加载），但它让「把罐建在目的地、人从远处回来」这个最自然的用法失效了。

## 2. 目标与非目标

目标：

1. 目标罐所在区块未加载时，客户端对**有授权的玩家**仍能给出真实池量；对没有授权的玩家不报价（详见 3.2 的三态）。
2. 服务端在实际传送时**确实**能读到那个罐并按罐优先扣费。
3. 代价可预算：单次传送默认最多加载 1 个区块（`tank.remotePaymentChunkLoadsPerTeleport`，0–4）；打开菜单不加载任何区块；每次菜单最多 32 条查询。

非目标：

- 不做「传送完成后再追扣」的结算（传送已发生，扣不动就只能追扣玩家，会与 E-1/E-3 的账目原则冲突）。
- 不让客户端一律乐观（那就是 C-2 记录的「按钮报价撒谎」）。
- 不保证跨维度目的地的罐（客户端没有该维度的方块实体，且跨维度传送的目标区块加载语义不同）。

## 3. 三个机制

### 3.1 池量索引（`data/TankPoolIndex.java`）

`SavedData`，存在主世界的数据存储里，键是「维度 + 罐位（`BlockPos.asLong()`）」，值是
`{poolXp, mbPerXp, updatedAt}`，另有哨兵 `NO_TANK = -1` 表示「确认这里没有罐」。

写入时机：

- 罐内容变化（`XpPaymentTankBlockEntity#onContentsChanged`）；
- 罐被载入（`loadAdditional` 末尾）——世界重入、区块重载后自我校准；
- 服务端在提示查询里看到一个**已加载但没有罐**的槽位（记 `NO_TANK`）。

删除时机：方块被移走（`XpPaymentTankBlock.onRemove`，只在方块真的变成别的方块时）。**不能**放进 `setRemoved`：
区块卸载也会走那里，那会把「远处的罐」从索引里删掉，正好毁掉这个特性。

上限 `MAX_ENTRIES = 4096`：只用于预览。写满后**新条目被丢弃**（不是淘汰最旧的），并打一条 WARN——索引坏了也不影响扣费，扣费永远以实物为准。

### 3.2 提示包（`net/XppTankHintQueryPayload` + `net/XppTankHintPayload`）

- 客户端：`client/XppTankHints` 在按钮报价时若「区块未加载且本地没记录」→ 把槽位排进队列；
  每个客户端 tick 最多发一个查询包（一次一个维度、最多 32 槽）。
- 服务端：`net/XppServerHandler#handleHintQuery` **不加载任何区块**，每个槽位回答一个「池量 + 使用权」二元组：

| 槽位状态 | 池量 | 使用权（`Access`） | 客户端据此 |
| --- | --- | --- | --- |
| 已加载、有罐、名单放行 | `poolXp` / `mbPerXp` | `ALLOWED` | 用池量做真实算术 |
| 已加载、有罐、名单不放行 | `0`（不报金额） | `DENIED` | 不当作付款方，也不显示"可付" |
| 已加载、没罐 | `NO_TANK = -1` | `UNKNOWN` | 按玩家 XP 判定（顺手把 `NO_TANK` 写进索引） |
| 未加载、索引有记录 | 记录的池量 | `UNKNOWN` | 按池量报价（保守放行，可能略旧） |
| 未加载、索引没记录，或总开关关闭 | `UNKNOWN = -2` | `UNKNOWN` | 保守放行、不报价；下个 tick 再问一次 |

  `DENIED` 时**不报金额**是有意的：让一个无权使用的玩家读到罐主的库存，等于给了一个免费的家底探针。
  `UNKNOWN` 永远保守放行（不置灰），这是本特性存在的理由——未加载区块里可能确实有罐。
- 三态由 `net/HintAccessRule.java` 一个纯函数决定：名单放行 → `ALLOWED`；不放行且该罐有队伍条目、但队伍模组没装
  （查不出对方在哪些队）→ `UNKNOWN`；其余不放行 → `DENIED`。没有队伍模组时不能把「不在名单里」当成证据。
- 客户端缓存 30 秒（`TTL_MILLIS`）；`UNKNOWN` 不算已知答案，下次打开菜单会再问一次。
- 该二元组随协议版本 `4` 上线（`event/XppModEvents.PROTOCOL_VERSION`），旧客户端会在握手里被明确拒绝。

三种答案必须可区分，这是全部设计里最容易退化的一处：把 `UNKNOWN` 当 `NO_TANK`，远处满罐的按钮就又灰了；
把 `NO_TANK` 当「未知」，则会点亮一个不可能付得起的按钮。

### 3.3 受限预加载（`payment/PayerBudget.java` + `XppTeleportHandler#tankBelow`）

服务端在真正传送前（`WaystoneTeleportEvent$Pre`）读目的地罐。位置由 `payment/TankPlacement#candidateTankPositions`
给候选：石碑形状可观测时只有一个位置；观测不到（区块未加载 → `RecordedHalf.UNKNOWN`）时「正下方」与「再下一格」
都算候选（去重、正下方优先；单格石碑与「记录落点在下半格」的双格石碑都收敛到正下方）。

1. 逐个候选先探 `Level#isLoaded`（`ChunkSource#hasChunk`，服务端客户端都不加载）：**已加载就直接读方块实体，
   绝不走载入路径**。`getBlockState` 与 `getBlockEntity` 在服务端都会隐式 `getChunk(…, ChunkStatus.FULL, true)`，
   先 `isLoaded` 才把「顺手加载」关住——否则读一个罐位就绕过了本节的配额；
2. **只有「没读到罐、且区块确实不在内存里」才申请配额**（默认 1，`tank.remotePaymentChunkLoadsPerTeleport`，0–4）。
   已经在内存的区块没有可加载的东西，问配额只会白花掉本次唯一的一次——源端石碑就在玩家脚下、
   又常常没罐，先探源端再探目的地时，这一下正是「第一次点击不走罐、第二次才走」的成因。
   两个候选只差 Y、同属一个区块，因此**一次**配额覆盖全部候选；
3. 通过后 `level.getChunk(x >> 4, z >> 4, ChunkStatus.FULL, true)`——**只加载已存在的数据，不生成地形**；
4. 重新探候选，按既有规则（非空、权限、池量）决定是否由它付款。`Payer` 记的是罐实体的真实位置
   （`tank.getBlockPos()`），不是推算出来的那个。

防抖：**只有加载过却没能读出罐**（失手）才把该位置记 5 秒（`PayerBudget#rememberMiss` → `RECENT_ATTEMPTS`），
免得连点把同一块区块反复拉进来。加载**成功**不记：区块在玩家离开后会被卸载，把成功记成失手会让下一次
去同一目的地的传送被自家防抖挡掉，玩家看到的就是「刚才还能付的罐，这次说经验不足」。
失败即回退：配额用尽、额度被防抖挡下、加载后仍取不到方块实体，一律按原逻辑回退到玩家付费（与 B6 行为一致，不会更糟）。

### 3.4 开关

```toml
[tank]
# 允许用远处（区块未加载）的目的地储罐付款。
remoteDestinationPayments = true
# 单次传送最多为读取目的地储罐而加载多少个区块（0 关闭该机制）。
remotePaymentChunkLoadsPerTeleport = 1
```

关闭 `remoteDestinationPayments` 时：服务端不再预加载，也不再为未加载槽位回答「没罐」，而是统一回答 `UNKNOWN`
（它确实不知道，预加载关掉后它也没有办法知道）。客户端对 `UNKNOWN` 保守放行、不报价——按钮按玩家 XP 判定，
传送时若罐确实读不到就退回玩家付费，与本特性之前的行为一致，但不会谎称「这里没有罐」。

## 4. 数据流（打开菜单）

```
Waystones 构建按钮需求
  └─ client mixin → XppClientRequirements.decorate
       ├─ 罐位候选（TankPlacement#candidateTankPositions）：形状可读到 → 1 个；区块未加载 → 2 个（正下方、再下一格）
       ├─ 任一候选就在本地（区块已加载）→ 直接读方块实体并记进 XppClientTankRegistry（原有路径）
       ├─ 都不在本地 → 两个候选都入 hints 队列（去重后最多 2 槽）
       │    └─ 选择交给纯函数 selectPayerSlot：已见证据（注册表）优先于提示；提示按候选顺序取第一个「算付款方」的
       │         ├─ 有答案且放行（ALLOWED / UNKNOWN + 池量）→ 包装成可付款需求，`canAfford` 用池量做真实算术
       │         ├─ 明确无权（DENIED）→ 不包装（按钮按玩家 XP 判定，不泄露池量）
       │         ├─ 已知无罐（NO_TANK）→ 不包装（按钮按玩家 XP 判定）
       │         ├─ 一个候选已知空罐、另一个报了池量 → 取报池量的那个（已知空罐不得遮蔽另一候选）
       │         ├─ 有答复但池量 UNKNOWN → 按「未知但许可」包装（不报价）
       │         └─ 一个候选都没答复 → 本次置灰，入队问服务端，下个 tick 拿到答案再定
```

排队 → 发包 → 回包 → 缓存，最多一个 tick 一轮；30 秒内重复打开菜单不再发包。

## 5. 失败模式

| 情况 | 行为 |
| --- | --- |
| 索引里是旧池量（罐被抽空/灌满但未再载入） | 报价可能偏旧；传送时服务端按实物算，付不起就拒绝传送（不会多扣） |
| 方块已拆但索引未清（历史数据） | 预加载发现没有方块实体 → 回退玩家付费 |
| 石碑记录落在上半格、且该区块未加载 | 服务端按 `RecordedHalf.UNKNOWN` 走两个候选（正下方、再下一格），命中真罐的槽位；客户端同样两个候选都问 |
| 客户端与服务端配置不一致 | 客户端只影响按钮；扣费永远以服务端为准 |
| 服务端拒绝加载（区块不存在/生成） | 取不到方块实体 → 回退玩家付费 |
| 同一 tick 打开多个菜单 | 队列合并，仍是最多一个包/tick、32 槽/包 |
| 玩家无权使用该罐（`DENIED`） | 客户端不把它当付款方、不显示池量；服务端在传送时同样拒绝，两边一致 |
| 罐的名单里有队伍条目、但队伍模组没装 | 判为 `UNKNOWN` 而不是 `DENIED`：查不出对方在哪些队，就不能说「不在名单里」 |

## 6. 已知限制

- 跨维度目的地不在覆盖范围内（客户端不加载该维度；且跨维度传送的区块加载语义需要单独设计）。
- 索引以「主世界数据存储」为家，若某整合包把所有维度换成自定义数据存储，需要复核 `TankPoolIndex#get`。
- 提示缓存 30 秒：刚被抽空的罐在最坏情况下仍显示旧池量 30 秒；授权判定同样按 30 秒刷新。
- 索引写满 4096 槽后不再记新槽位（打一条 WARN），旧槽位的报价仍按记录走。
- 区块未加载时候选固定两个（正下方、再下一格），依赖「罐紧邻石碑下方」的摆放规则；更远处/别的方向的罐读不到。
  两个候选必然同区块（只差 Y），这也是「一次配额覆盖全部候选」的前提。

## 7. 验收要点

新增用例见 `docs/测试流程.md` 的 E11–E14：

- E11 远处目的地罐（区块已卸载）按钮可点亮；
- E12 实际传送后扣费来自该罐（日志 `Teleport paid from the destination tank`）；
- E13 5 秒内连续两次点击只加载一次区块；
- E14 `remoteDestinationPayments = false` 时不再报价、按钮按玩家 XP 判定（配置生效）。

单元测试：`PayerBudgetTest`（预算与 5 秒防抖）、`XppTeleportHandlerTest`（只有「没罐且区块不在内存」才花配额）、
`TankPlacementTest`（已加载上半格/下半格/单格的唯一解，
未加载时两个候选的去重与顺序，以及「未知答案必须覆盖两个已知答案」）、`XppClientRequirementsTest`
（`selectPayerSlot`：已见证据优先于提示、空罐不遮蔽另一候选、`DENIED` 与 `NO_TANK` 不付款）、`XppTankHintQueryPayloadTest`（去重/上限/三种答案语义）、
`XppTankHintPayloadTest`（三态往返、`DENIED` 不带金额、`UNKNOWN` 保持许可）、`HintAccessRuleTest`（三种裁决，
含「无队伍模组不得判 DENIED」）、`XppAccessPayloadTest`（模式字段往返、label 不影响模式）、`TankPoolViewTest`
