## §2 交互状态机

### 五态定义

| 态 | 代码条件 | 行区内容 | 输入框 | 菜单 |
|---|---|---|---|---|
| LIST 名单 | `!picking() && view==LIST` | `rows`（访问列表） | 可见、可获取焦点 | 可叠加 |
| PICKER 候选 | `picking()`（`searchBox.isFocused()`） | `found`（过滤后候选） | 焦点态 | 可叠加 |
| MENU 菜单展开 | `menuOpen`（叠加标志，记录 `menuSource ∈ {LIST,PICKER,MEMBERS}` 与 `menuRow`） | 底层态不变，菜单画在最上 | 冻结（不接收输入） | — |
| MEMBERS 成员查看 | `view==MEMBERS`（独占行区） | 成员行 | **隐藏** | 不叠加 |
| READONLY 只读 | `state != null && !state.canEdit()` | 仍显示 `rows`（可看、可选中） | 隐藏、按钮隐藏 | 可叠加（项全禁用） |

### 行为矩阵（5 态 × 7 输入）

| 态 \ 输入 | 左键 | 右键 | 滚轮 | ESC | ENTER | ↑ / ↓ | TAB |
|---|---|---|---|---|---|---|---|
| **LIST** | 行体→选中该行(单选)；空区→清选中+`setFocused(null)`；输入框框内→进 PICKER；`x≥229`→发 REMOVE_*；按钮→按钮回调 | 行上→选中该行+开 MENU(`source=LIST`)；其他→关 MENU，不选中 | 行区 `x∈[8,245)` 且 `count>cap`→滚 1 行 | ① MENU 开→关 MENU；② 否则 `super`（关界面） | MENU 开→激活高亮项；否则无动作 | MENU 开→菜单项高亮；否则无动作（行高亮只在 PICKER 生效） | 不拦截→vanilla 焦点循环 |
| **PICKER** | 行体→发 ADD_PLAYER/ADD_TEAM + 进 pending；空区→`clearSearch()` 回 LIST；输入框→保持焦点 | 候选行→**保留查询**+开 MENU(`source=PICKER`)；其他→关 MENU | 作用于 `found`，规则同 LIST | ① MENU 开→关 MENU；② 否则 `clearSearch()` 回 LIST；③ 已空→`super` 关界面 | MENU 开→激活；否则高亮行→`addCandidate` | MENU 开→菜单项高亮；否则移动行高亮（含单行滚动） | 不拦截；焦点离开 searchBox 会隐式退化为 LIST（≈ESC②，可接受，不额外处理） |
| **MENU** | 菜单内→执行该项（禁用项无反应、菜单保持开启）；**菜单外→关 MENU 且吞掉本次点击**（`return true`，不穿透到行/输入框） | 另一行→关旧菜单 + 在新行重开（**换行跟随：选中移到新行**）；同一行→关闭（toggle）；菜单外→关闭 | 任意位置→关 MENU 且**不滚动**（避免菜单错位） | 关 MENU，回 `menuSource`（PICKER 保留查询与行高亮；MEMBERS 保留成员列表） | 有高亮项→激活；**无高亮项→无动作**（首开不预置高亮，防误删） | 菜单项高亮移动（跳过禁用项）；不动行高亮 | 关 MENU（不穿透、不动焦点） |
| **MEMBERS** | 成员行→仅选中（不发请求）；返回控件 `(232,102,12,12)`→回 LIST；其他→无 | 不响应（成员行无可执行项，菜单不开） | 成员行区→滚动成员列表 | 回 LIST（第一段）；LIST 上再 ESC 才关界面 | 焦点在返回控件→回 LIST；否则无 | 成员行高亮移动（`highlightRow` 仅视觉）+ 单行滚动 | vanilla 焦点循环（返回控件注册为 widget，TAB 可达） |
| **READONLY** | 行体→选中（可读 UUID）；输入框/按钮已隐藏→落空；空区→清选中 | 行上→开 MENU（三项全禁用，含「查看」）；其他→关 MENU | 可滚（列表可见） | `super` 关界面 | 无动作 | 无动作 | 跳过隐藏按钮的焦点循环 |

**READONLY 下「查看队伍成员」禁用**的理由：`XppServerHandler.handle` 对 `REFRESH` 也做 owner gate（注释明写"owner check protects every action, REFRESH included"），只读玩家发出去必被拒 → 不做会必然失败的控件，直接置灰。

### 态间切换规则

| 迁移 | 触发 | 副作用 |
|---|---|---|
| LIST → PICKER | 输入框框内左键 / 焦点进入 | 保留 `rows`；`found` 由 `applyFilter()` 重建；`scrollOffset=0` |
| PICKER → LIST | 空区左键 / ESC② / `clearSearch()` | 清查询、丢焦点、`lastQuery=""`、`highlightRow=-1`、`scrollOffset=0` |
| LIST/PICKER/READONLY ↔ MENU | 右键行（开，`menuRow=该行`）/ 菜单外左键（关+吞）/ 右键他行（换行重开）/ ESC / ENTER（执行后关） | 关闭时 `menuOpen=false, menuRow=-1`，不清选中 |
| LIST/PICKER → MEMBERS | MENU 的「查看队伍成员」（队伍行，可用态） | 关闭 MENU；`view=MEMBERS`；发 `REQUEST_MEMBERS`；`membersState=LOADING`；`scrollOffset=0`；**清行高亮** |
| MEMBERS → LIST | 返回控件 / ESC | `membersState=IDLE`；保留 `rows` 的 `scrollOffset` 与选中 |
| 任意 → READONLY | 新快照 `canEdit=false` | 强制关 MENU + 退出 MEMBERS + 隐藏输入框与 header 按钮 + 清 pending（并清状态条右段） |
| PICKER → （任意）快照到达 | `onState()` | 现状保留 `scrollOffset`/`highlightRow`；再 `clampScroll()` |

**三条不变量（验收点）**
1. **菜单外点击关闭且不穿透**：`mouseClicked` 首行判 `if (menuOpen) { if (inMenu(x,y)) 执行 else 关闭; return true; }`。
2. **右键换行跟随**：菜单开启时右键另一行 → 选中移到新行、菜单按新行重新定位；右键同一行 → 关闭。
3. **ESC 三段**：`MENU → PICKER(clearSearch) → super(关界面)`。即使 `searchBox` 未聚焦，只要 `menuOpen` 就**先**关菜单；`view==MEMBERS` 时 ESC 第一段是回 LIST。

### 翻转判定与坐标公式

```java
int w = menuWidth(), h = 60;
int x0 = cx, y0 = cy;                          // cx/cy = 右键处的面板内坐标
if (x0 + w > PANEL_RIGHT)      x0 = cx - w;    // 右边缘：整体左移到光标左侧
x0 = clamp(x0, ROW_LEFT, PANEL_RIGHT - w);     // 8 .. 248-w
if (y0 + h > PANEL_BOTTOM - 1) y0 = cy - h;    // 下边缘：整体上移到光标上方
y0 = clamp(y0, 0, PANEL_BOTTOM - 1 - h);       // 0 .. 179
```
`PANEL_BOTTOM` = 240（`PANEL_HEIGHT`），减 1 是让下边框不压在面板底边上。`clamp` 仅在极端小坐标（如 `cx=100, w=126`）触发，此时菜单覆盖光标——可接受，不做二级避让。
第 4/5 行的具体落点（行区间：0-based `i=3 → y=177..197`；`i=4 → y=198..218`）：

| 右键位置（面板内） | w | 判定 | 落点 `(x0,y0)` | 菜单占位 |
|---|---|---|---|---|
| 第 1 行 `(140,124)` | 96 | 不翻 | `(140,124)` | x140..236, y124..184 |
| **第 4 行** `(140,187)` | 96 | 下翻 | `(140,127)` | x140..236, y127..187 |
| **第 4 行** `(230,187)` | 96 | 右翻 + 下翻 | `(134,127)` | x134..230, y127..187 |
| **第 5 行** `(140,208)` | 96 | 下翻 | `(140,148)` | x140..236, y148..208 |
| **第 5 行** `(230,208)` | 96 | 右翻 + 下翻 | `(134,148)` | x134..230, y148..208 |
| **第 5 行** `(140,208)` | 126（en） | 右翻 + 下翻 | `(14,148)` | x14..140, y148..208 |

上翻/左翻后光标恰好落在菜单**右侧/下侧的边界外**（底边与右边为开区间），不会盖住光标所指的行。

### 绘制层级（从下到上）

`renderBg` 面板底/上下边框/分隔线 → 输入框框 → 行/成员行（hover 底 → 选中填充 → 选中外框 → 色条/图标/文字/✔ → 键盘高亮内框 → pending 三点）→ 滚动条 → 状态条（223..239）→ **菜单阴影 → 菜单底 → 菜单边框 → 三项** → （菜单开启时无 tooltip）。

- **菜单 > tooltip（硬性抑制而非靠顺序）**：`renderRowTooltip` 在 `menuOpen` 时直接 `return`；同时 `render()` 末尾的 `super.renderTooltip(...)` 也在 `menuOpen` 时跳过。理由：tooltip 是 `render()` 最后一步画的，如果只调层级顺序它必然盖住菜单。

## §4 选中态

**结论：单选（`selectedRow` 至多 1 行）。** 理由：① 协议 `XppAccessPayload` 每次只带**一个** `target`，批量操作要新增协议且服务端 `XpPaymentTankBlockEntity.access()` 无批量事务；② §6 的差集判定以单个 target 为单位，多选会让"哪一条生效了"不可判定；③ 右键菜单与成员查看都是单行语义。
选中键：`(team, id)`；`id==null` 的 legacy 行退化为 `(team, label)`。快照到达后重新绑定，找不到则清空。筛选、滚动、ESC 都**不**清选中；只有点击行区空区才清。

### 四通道分离（可同时存在）

| 通道 | 表现 | 颜色 / 坐标 |
|---|---|---|
| **选中** selection | 2px 外框 + 8% 填充 | 框 = 行类型强调色（player `0xFF4A9BE8` / team `0xFFE8A33D`）；填充 = `0x22` + 同色高 6 位。框 `(ROW_LEFT, y, 237, 20)`，用两次 `renderOutline` 内缩 1px 得 2px 效果 |
| **hover** | 仅行底调亮（现状不变） | `0x55FFFFFF` / `0x55E8A33D` |
| **键盘高亮** highlight | 1px 内框 | `0xFF9A9A9A`（`COLOR_HIGHLIGHT`），`renderOutline(8, y, 237, 20, 0xFF9A9A9A)` |
| **「我」✔** | 文字字形 | `0xFF7CFF9A`，位置不变（`TEXT_LEFT + prefixW + labelW + 4`） |
| **pending 脉动** | 行尾三点（§6） | `0xFF55FF99`，中心 x = 209/214/219，y = 行 y+10 |

**键盘高亮与新选中态的关系**：两者是不同通道，可同时存在（鼠标选中一行、键盘走位到另一行时两个框同时可见，这是刻意的——键盘走位不应清掉鼠标选中）。规定：`highlightRow == selectedRow` 时**只画键盘框**（1px 灰）并**把选中外框降级为仅填充**，避免同位置双框互相干扰、也避免"这个行到底是选中还是高亮"的歧义。
**落地 delta**：现行代码 `drawRow` 里的 `renderOutline(ROW_LEFT, y, ROW_RIGHT - ROW_LEFT - 8, 20, COLOR_HIGHLIGHT)` 宽度为 **229**（留出 8px 删除列），§1 定为 **237**（全行宽）。改为 237 后两框同宽，选中 / 高亮仅靠颜色、填充、线宽区分——这正是本节的前提。

## §5 队伍成员查看面板

**不新开 Screen**：复用同一 256×240 面板与同一行区 `y=114..219`，只换标题、行源与底部状态条左段。

| 元素 | 坐标 / 规格 |
|---|---|
| 标题 | `HEADER_X=12, HEADER_Y=104`，`access.members.header`「队伍：%s」；标签用 `fit()` 截断到 `232-6=226` 之前 |
| 返回控件 | `(232, 102, 12, 12)`，字形 `<`，色 `COLOR_MUTED`；**注册为 `AccessButton`**（强调色 `0xFFAAAAAA`）以便 TAB 可达 + ENTER 可触发（自绘 hitbox 会让成员态出现"无任何 TAB 可达控件"的无障碍洞） |
| 成员行 | `y = 114 + i*21`，行体高 20；`ROW_LEFT=8` → `ROW_RIGHT=245`；色条 3px `0xFF4A9BE8`；图标 = 8×8 实心方块 @ `ICON_LEFT=15`；文字 @ `TEXT_LEFT=27`，前缀 `[P] ` |
| 成员颜色 | 在线：文字 `0xFFFFFFFF`，状态点 `●` `0xFF7CFF9A`；离线：文字 `0xFF8A8A8A`，状态点 `○` `0xFF8A8A8A`。状态点右对齐，右边界 = `LABEL_RIGHT`(205) |
| 悬浮提示 | 悬停 500 ms 后显示该成员 UUID（与行 tooltip 同路径、同 `0xFFAAAAAA`） |
| 删除列 | **不画 ×**；`DELETE_X` 区不参与命中 |
| 滚动条 / 分页 | 复用 `drawScrollbar`（`x=245, w=3, color=COLOR_MUTED`，轨 `COLOR_SEPARATOR`），**每滚一行，不做分页**（分页要引入页码状态与页内选中，而 5 行视口 + 滚轮已足够；成员上限由队伍规模决定，不是用户数据量级） |

### 成员行能否「添加 / 删除该成员」

**结论：不能（成员行只读，右键菜单不打开）。** 理由：① 访问列表条目以**队伍为整体**（`access.teams()` 存 `teamId`），单独加一个成员会与队伍后续真实成员分叉；② "单独删掉这个成员"在语义上是"把该队伍排除这个人"，协议（`ADD_TEAM/REMOVE_TEAM`）无此表达，硬做等于说谎；③ 服务端 `XppServerHandler.addPlayer` 只接受**在线** UUID（`onlinePlayers()` 检查），离线成员点了必然被拒 → 同一个控件一会能用一会不能用，是最坏的可发现性。
替代路径：要给单人授权 → 名单模式 → 候选模式搜索该玩家（候选 `candidatesPlayers` 只含在线玩家，一致）。

### 状态与文案

|---|---|---|---|
| LOADING | 发出 `REQUEST_MEMBERS` 后 | `access.members.loading` | 居中文案 + 滑动进度条（见下） |
| OK·空 | `status=0` 且 `members=[]` | `access.members.empty` | `drawCentered` / `COLOR_MUTED` |
| NO_TEAM_MOD | `status=1` | `access.members.no_team_mod` | 同上 |
| UNKNOWN_TEAM | `status=2`（队伍已解散） | `access.members.unknown_team` | 同上，返回控件仍可用 |
| NOT_OWNER | `status=3` | `access.members.denied` | 同上 |

### 数据字段清单（客户端拿不到 FTB 成员，必须服务端下发）

按你的形状实现，但**必须增加两个字段**，否则 §2/§6 的状态机无法闭合：

```java
XppTeamMembersPayload(
    BlockPos pos,          // writeBlockPos
    UUID     teamId,       // UUIDUtil.STREAM_CODEC（teamId 为 null 的 legacy 队伍行不发此请求）
    String   teamLabel,    // writeUtf(64)，服务端权威名（队伍可能已改名，客户端只有旧快照）
    byte     status,       // 0=OK 1=NO_TEAM_MOD 2=UNKNOWN_TEAM 3=NOT_OWNER
    long     requestId,    // ★新增：请求/应答配对
    List<Member> members   // VarInt 长度 + 每项 (UUIDUtil.STREAM_CODEC(id), writeUtf(name,64), writeBoolean(online))；服务端上限 256 截断
)
Member(UUID id, String name, boolean online)
```
- `requestId` 必要：同一队伍连续两次「查看」（关闭后重开、超时重试）会让**先发的回包**落在后一次请求上；没有 id 就无法丢弃过期回包，加载态的结束时机就是错的。
- `status` 必要：空数组无法区分"队伍没有成员"与"服务端没有队伍模组 / 队伍已解散"，而这两者文案不同。
- `members[]` 含 `online`：在线与否决定文字色与状态点，且**离线成员不可被 ADD_PLAYER**（§5 结论③）。
- 服务端来源：`TeamResolver` 新增 `List<MemberInfo> membersOf(UUID teamId)`（`MemberInfo = (UUID id, String name, boolean online)`）；FTB 实现走反射 **[NEEDS VERIFICATION: FTB Teams 2101.x 的 Team 成员访问器名（`getMembers()` 返回 `Collection<UUID>`，或 `getOnlineMembers()`）—— 需在实机上 `javap` 确认后再定方法名，不得照猜]**；`online` 由 `MinecraftServer.getPlayerList().getPlayers()` 的 UUID 集合判定；无队伍模组 → `status=NO_TEAM_MOD`。
- 权限：与其它动作同一道 owner gate（`XppServerHandler.handle` 对 `REFRESH` 也查 owner）→ 只读玩家得到 `NOT_OWNER`。
- 请求侧：`XppAccessPayload.Action` 新增 `REQUEST_MEMBERS`（`target=teamId`、`label=teamLabel`）。**协议变更**。

### 差集判定（回包后"我的请求生效了吗"）

登记表深度恒为 1（发送中禁用全部写控件，见上）：`PendingRequest{Action action, UUID target, String label, boolean wantWhitelist, long sentAt, long requestId}`。判定全部基于**回包快照** `XppStatePayload.entries()`：

| action | 期望 | 判定 |
|---|---|---|
| ADD_PLAYER | `entries` 存在 `!team && id==target` | 命中 → 成功；未命中 → 被拒 |
| ADD_TEAM | `entries` 存在 `team && id==target` | 同上 |
| REMOVE_PLAYER | `entries` **不**存在 `!team && id==target`；`id==null` 的 legacy 行再比 label | 命中 → 成功；仍存在 → 被拒 |
| REMOVE_TEAM | `entries` **不**存在 `team && (id==target \|\| label 相等)` | 同上 |
| SET_MODE | `snapshot.whitelist() == wantWhitelist` | 相等 → 成功；不等 → 被拒 |
| REQUEST_MEMBERS | 收到 `requestId` 匹配的 `XppTeamMembersPayload` | `status==0` → 成功；否则按 status 文案 |

**幂等例外（必须显式处理，否则会误报成功）**：ADD 一个**已经在列表里**的目标时，服务端 `AccessList.add*` 返回 `false`、但仍推快照（`handle` 里的 `sendTo` 无条件执行）→ 目标本就在 `entries` 里，"命中"会误判为"添加成功"。规则：发送前记录 `wasPresent`；`wasPresent==true` 时**根本不下发**（菜单把「添加」置灰，见 §3），从源头消除，而不是拿回包去猜。
**超时的含义**：服务端在**每一条**路径（含 deny、含 add 被拒）都会推快照，所以"3000 ms 内没有任何新快照"只可能是丢包 / 断线 / 屏幕已关 → 文案就写成"服务端无响应"。
