## 代码质量分析

### 优点（本轮改动里值得保留的）

1. **收口方向对**：`canEditOrOp` 把「谁能编辑」从一个协议字段 + 一处服务端判断，收成一个方法；界面与服务端读同一个调用，分叉不再可能。
2. **纯函数做可测接缝**：`editAllowed`、`PlayerNames#label` 与既有 `pickPool` 同一套路，规则与 `MinecraftServer` / `Level` 解耦，负向验证（把 `editAllowed` 改成 `return ownerOrTeamMate`）能立刻红。
3. **注释写的是教训而非步骤**：`playerId` 为本人时不算 legacy row、`getMembers()` 是 Set 所以排序、被拒也要回快照——都是「不写就会被后人改坏」的信息。
4. **降级路径明确**：`PlayerNames#remembered` 对 null server / null cache 逐个返回 null 并写清契约，没有静默 NPE。

### 根因

四点，前两点是本轮真正的机制性问题：

1. **「同一个事实」的收敛只做了一半**：第二轮把**数据源**（档案缓存、短 id）收进了 `PlayerNames`，但把**优先级**
   留在两个包里各写一遍。只要优先级还在两处，`isBlank` 这类细节迟早分叉——本轮已可观测到分叉。收敛要以「谁会
   被后人改坏」为准，不是以「哪几行长得像」为准。
2. **注释写在「我知道答案的地方」，而不是「读者会出错的地方」**：`canEdit` 的 javadoc 花三行讲 `canEditOrOp`
   的理由；`XppServerHandler` 的注释还在描述已经被替换掉的旧代码。补注释时跟着改动点走，改完没回头删旧的那一半。
3. **说明性断言缺少可验证性**：`PlayerNames` 类 javadoc 的「both printed the raw id」这种历史断言没有测试也没有
   引用可对，写的时候「听起来对」就留下了。写历史/因果类注释前先 `git show` 对一遍旧实现。
4. **风格声明缺位放大了前三点的成本**：没有 `AGENTS.md` 的风格节，每一轮都要临时判断「注释写到什么程度、要不要抽纯
   函数」，判断结果散落在各轮 diff 里，没人能引用。
