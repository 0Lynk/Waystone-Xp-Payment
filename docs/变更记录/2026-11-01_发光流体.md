# 发光流体

日期：2026-11-01
分支：`feat/glowing-fluid`

## 改了什么

1. 新增 `src/main/java/com/olynk/waystonexppayment/client/TankLight.java`：`static int packed(int packedLight, int fluidLuminance, int fullBrightness)` —— 流体声明了亮度就用满亮，否则用所在位置的光。
2. `client/XpPaymentTankRenderer#render` 用 `TankLight.packed(...)` 计算光照，`LightTexture.FULL_BRIGHT` 由调用方传入（让 `TankLight` 不依赖 Minecraft 类，可单测）。
3. `block/XpPaymentTankBlock#getLightEmission` 新增：罐里装的是会发光的流体时，方块本身按流体亮度照亮周围。
4. 新增 `src/test/java/com/olynk/waystonexppayment/client/TankLightTest.java` 三例。

## 为什么改

机主：某些经验流体会发光（EIO 和 Create 的罐子会让它们亮起来），我们的罐子把它们画得和普通流体一样暗。

## 根因

上一版只做了「画液面」这件事，光照直接用了方块位置的光（`packedLight`）。发光流体在数据上是有亮度声明的（`FluidType#getLightLevel`），但代码从没读过它；方块也没有实现 `getLightEmission`，所以罐子既不发亮也不照周围。

对照 EnderIO 的 `FluidTankBlock#getLightEmission` 字节码，它的做法正是：取方块实体里的流体 → `getFluidType().getLightLevel()` → 直接返回。两处（方块发光 + 液面满亮）都要有，否则要么房间发亮而液面发暗，要么反过来。

## 改动前后对比

| | 之前 | 现在 |
|---|---|---|
| 液面光照 | 永远取方块位置的光 | 流体有亮度 → `FULL_BRIGHT`，否则取位置光 |
| 方块发光 | 无（`getLightEmission` 默认 0） | 返回当前流体的亮度，房间会被照亮 |
| 暗室里装发光流体 | 液面暗、房间也暗 | 液面满亮、房间发亮 |

## 备选方案

- **a. 只在渲染器里提亮**：房间还是黑的，玩家会看到一个亮液面浮在黑暗里，比不改更怪。
- **b. 只在方块上加 `getLightEmission`**：房间亮了，但液面用的是位置光——在某些角度仍是暗面，液面与光晕对不上。
- **c. 用 `RenderType` 的自发光变体（如 `eyes`）**：会绕过光照系统，而且 `eyes` 不透明、不带 alpha，半透明流体不能用。
- **选 a + b 的组合**：两处都按同一个 `getLightLevel` 走，规则一致。

## 意外点

- `FluidType` 有两个重载：`getLightLevel()` 与 `getLightLevel(FluidStack)`。方块里只能用无参版本（`BlockGetter` 拿不到 stack 的上下文），渲染器用带 stack 的版本，两者在默认实现里等价。
- `getLightEmission` 会被光照引擎频繁调用，所以先判 `isLoaded` 再取方块实体，避免为了算亮度去加载区块。
- `LightTexture.FULL_BRIGHT` 是客户端类，塞进 `TankLight` 会让它无法在纯 JVM 测试里加载，所以改成参数传入。

## 验证

- `.\gradlew.bat test --offline` → **30 suites / 182 tests / 0 failures**（179 → 182）。
- 负向验证：把 `TankLight.packed` 改成恒返回 `packedLight` → `aGlowingFluidIgnoresTheRoom` 红，还原后全绿。

## 未覆盖

- 只有策略层单测；方块发光与液面亮度都要靠实机确认（尤其要看发光流体在暗室里的房间亮度）。
- `getLightEmission` 的 `isLoaded` 守卫在客户端光照重算时是否会有可见延迟，需实测。
