# 2026-10-11 所有者权限与输入候选界面

## 改了什么

### 权限模型：储罐所有者
- `XpPaymentTankBlockEntity` 新增 `@Nullable UUID ownerId` 与 `String ownerName`（NBT 键 `XppOwner` /
  `XppOwnerName`，UUID 用 `UUIDUtil` 存成 int 数组），以及 getter、`setOwner(UUID, String)`、
  `isUnowned()` 与 `canEdit(Player)`。
- `XpPaymentTankBlock.setPlacedBy(...)` 在放置者是 `ServerPlayer` 时把放置者写为所有者。
- `canEdit` 规则：`ownerId == null` → true（旧罐未认领）；发送者 UUID == ownerId → true；否则
  `TeamResolvers.get().teamsOf(owner)` 与 `teamsOf(player)` 有交集 → true；其余 false。
- `TeamResolver` 接口新增 `default List<TeamInfo> teamsOf(UUID playerId) { return List.of(); }`，
  `FtbTeamsResolver` 用同一套反射按 UUID 实现（`TeamManager.getTeamForPlayerID(UUID)`），
  `TeamResolver.NONE` 保持空表。`teamsOf(Player)` 现在委托给 `teamsOf(player.getUUID())`。
- op 命令路径未改：`XppCommands` 仍要求权限等级 2，`XppServerHandler` 对 op 的命令语义不变。

### 协议
- `XppStatePayload`（record + StreamCodec）新增 `boolean canEdit`、`String ownerName`、
  `List<Entry> candidatesPlayers`、`List<Entry> candidatesTeams`，共 12 个字段；沿用既有 `Entry` 编解码与
  列表长度前缀写法，不做旧版本兼容（服务端与客户端同版本）。
- `sendTo(...)` 内部填充：`canEdit = tank.canEdit(player)`；`ownerName = tank.ownerName()`；
  `candidatesPlayers` = 服务端在线玩家去重后按名字排序（`Entry(uuid, name, false, false)`）；
  `candidatesTeams` = `TeamResolvers.get().allTeams()`（`Entry(id, name, true, false)`）。
- `XppServerHandler` 改为：`!tank.canEdit(player) && !player.hasPermissions(2)` → 日志 + 聊天
  `access.no_permission` + 回发最新状态并 return；
  `ADD_PLAYER` 的 target 必须是在线玩家 UUID，`ADD_TEAM` 的 target 必须是已知队伍 UUID，否则同样拒绝；
  任何成功改动后若生效且 `ownerId == null` → 认领（INFO 日志 + 聊天 `access.claimed`）；
  最后统一回发状态。`SET_MODE` / `REMOVE_*` / `REFRESH` 语义不变但同样受 `canEdit` 限制。
  **与任务书的一处偏差**：任务书同时要求“先判 `canEdit` 不通过就拒绝”和“op 命令路径不变（权限等级 2）”。
  两条在字面上互相矛盾——按前者，非 op 的普通玩家即便放下储罐拥有所有权，界面上 `canEdit == true`
  可编辑，服务端却在 `canEdit` 之前就把非 op 全部拒了，等于所有者规则对他完全不生效。这里把门禁合并成
  “所有者/同队 **或** op”，两边都保留：op 是所有者不在时的管理后门，所有者规则对普通玩家真正生效。

### 客户端界面
- 面板改为 256×240（原 256×214），`XpPaymentTankMenu` 暴露 `PANEL_WIDTH` / `PANEL_HEIGHT`；
  GUI 高度 < 240 时可见行数从 5 降到 4。
- 修掉坐标：`renderBg` 与 `render` 的自绘部分都先 `pose().translate(leftPos, topPos, 0)` 再画，命中测试继续用
  面板相对坐标；删掉 `render()` 里显式调用的 `renderBackground`（`super.render` 已经调过一次）；
  `renderLabels` 置空，标题自己画。
- 新增 `client/AccessButton extends Button`：自绘底/顶高光/底阴影/左侧 3px 强调色条/四边 1px 边框 + 文字，
  强调色 = 该按钮插入那一行的颜色（模式灰、添加我蓝、添加我的队伍琥珀），不新增贴图。
- 新增输入框 + 候选列表：`EditBox`（`setBordered(false)`，`setMaxLength(32)`）未聚焦时行区是访问条目列表，
  聚焦时变成候选列表——在线玩家（蓝行）在前、全部队伍（琥珀行）在后。
- 打字只做本地过滤（忽略大小写 contains，前缀命中排前），客户端不解析名字也不把名字发服务端；加入时提交候选
  行自带的 UUID。提到过的重复项在服务端二次校验（只接受在线玩家 UUID 与已知队伍 UUID）。
- 键盘：`Esc` 两段式（先清查询并 `clearFocus` 回条目列表，再按才交给 `super` 关界面）；`Enter` 加入键盘高亮
  候选；`↑/↓` 移动高亮并自动滚动一行；`Tab` 放行给 vanilla 焦点循环。
- 鼠标：点输入框外框任意处即聚焦；行内 `×` 热区（229..245）优先于整行点击；候选行点击 = 加入；点空白
  `clearFocus()`。
- 状态：`state == null` → 三按钮与输入框隐藏 + 行区居中 `access.waiting`；`!canEdit` → 只读态（输入框与三个新增
  按钮隐藏而非禁用、行不画 `×` 且不可点、行区居中 `access.readonly` 带所有者名）；条目为空 → `access.list.empty`；
  两类候选都空 → `access.picker.no_candidates`；单类空 → `access.picker.no_players` / `no_teams`（画在列表头下方
  一行）；查询无结果 → `access.picker.no_match`，输入框边框闪一次 0xFFE05555（150ms）。
- 滚动条 245,114→248,219（track 0xFF555555，thumb 高 `max(10, 105*VISIBLE/count)`）；滚轮只在指针位于行区时接管。
- 行 tooltip 显示完整 UUID，画在 `super.renderTooltip(...)` **之后**；EditBox 聚焦时、指针在按钮或输入框外框内时、
  指针所在行 == 键盘高亮行时不画。键盘高亮用 `renderOutline(8,y,237,20,0xFF9A9A9A)`，鼠标 hover 用底色。

### 语言与文档
- `lang/en_us.json` / `lang/zh_cn.json` 键集完全一致（30 键），新增 `access.readonly`、`access.owner`、
  `access.owner.none`、`access.picker.header`、`access.picker.hint`、`access.picker.no_candidates`、
  `access.picker.no_players`、`access.picker.no_teams`、`access.picker.no_match`、`access.no_permission`、
  `access.claimed`（原有键全部保留）。
- README 的“访问控制”一节改写：新增所有者/只读/未认领首次编辑即认领的说明，以及输入过滤 + 候选选择的用法。

## 为什么
第一轮把访问列表做成了可点列表，但只有“我”和“我的队伍”两个入口，加入别的玩家/队伍只能靠 op 命令；同时面板
坐标没做 `translate`，自绘内容和命中测试差了一个 `leftPos/topPos`，在窗口里偏出去。需求同时要求“只有储罐所有者
及其队伍成员可以修改”，否则任何人都能把别人的储罐改成白名单空表（等于关掉它的支付）。

## 取舍
- **候选列表由服务端下发，而不是客户端自己拼**：客户端不知道在线玩家名册，也不知道全部队伍列表；下发一份让客户端
  只做本地过滤，加入时回传候选行自带的 UUID，服务端再按“必须是在线玩家 / 必须是已知队伍”二次校验。代价是每个快照
  多传两个列表，收益是客户端永远无法凭一个手打的名字伪造身份。
- **不新增贴图**：`AccessButton` 自绘、队伍图标复用 `container/enchanting_table/level_1`，因为资源包里没有可用的
  按钮/图标贴图，加贴图会破坏“改代码”的边界。
- **`canEdit` 只在 `Player` 上判定，不看 op**：op 的命令路径单独保留权限等级 2 的检查，避免 GUI 的只读态和命令的
  管理员能力互相污染（管理员可以改任何罐，但不是所有罐都会在界面上显示成可编辑）。
  服务端门禁因此写成 `canEdit || hasPermissions(2)`，而不是“先 op 再 canEdit”或“先 canEdit 再 op”。
- **认领只发生在“成功改动”之后**：`SET_MODE` 改成当前已有模式、删除不存在的条目都不算改动（`setMode`/`remove*`
  返回 false 时不认领），否则一个误点就能把公共储罐锁死。
- **旧协议不兼容**：前后端同版本分发，新增字段直接改 record 顺序，省掉版本号判定的复杂度。

## 修复（同日补充）

### 右键储罐即被踢出（“网络协议错误”）
- 现象：右键储罐后客户端报**网络协议错误**并断开连接，单人存档一样发生。
- 根因：`XpPaymentTankScreen.init()` 由 `ClientboundOpenScreenPacket` 触发，而这个包比状态快照包**先**到达客户端，
  所以第一次 `init()` 时 `state` 仍是 null；`refreshWidgets()` 里
  `addTeamsButton.active = !state.ownTeams().isEmpty();` 直接解引用，NPE 逃出数据包处理器，被 NeoForge 判成协议
  错误并踢人（日志原文）：
  ```
  [Render thread/ERROR] ClientCommonPacketListenerImpl: Failed to handle packet ClientboundOpenScreenPacket
  java.lang.NullPointerException: Cannot invoke "XppStatePayload.ownTeams()" because "this.state" is null
      at XpPaymentTankScreen.refreshWidgets(XpPaymentTankScreen.java:277)
      at XpPaymentTankScreen.init(XpPaymentTankScreen.java:155)
  ```
- 修法：该行改为 `state != null && !state.ownTeams().isEmpty()`；同时复核了 init 与渲染路径上其余 `state` 解引用
  （`drawPool`、`drawHeader`、`drawList`、`renderRowTooltip`、`mouseClicked`、`keyPressed`、`isSelfListed`），它们本来
  就带 null 防护——这正是快照到达前显示 `access.waiting` 的原因。
- 教训：**在数据包处理器里抛异常等于断开连接**，而不是崩溃报告。凡是数据包能直接调到的入口（`init()`、快照回调）
  都必须把“服务器还没回话”当作正常状态处理。
