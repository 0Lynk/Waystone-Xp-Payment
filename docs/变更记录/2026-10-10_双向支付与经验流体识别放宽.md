# 2026-10-10 双向支付 + 经验流体识别放宽

## 改了什么

- `event/XppTeleportHandler`：支付来源改为"**先看来来源石碑下方的罐，再看目标石碑下方的罐**"；每次成功接管
  都写一条 INFO 日志（来源槽位、流体 id、匹配原因、池 XP、本次花费），跨维度且目标区块未加载时回退给玩家。
- `client/XppClientRequirements`：客户端预览同样支持"目标石碑下方有罐"（跨维度目标不猜测，保持原判定）。
- `fluid/FluidRateTable`：
  - 新增**静流/流动流互认**（声明 `x:experience` 也认 `x:flowing_experience`，反之亦然）；
  - 新增**经验命名识别**（id 路径按 `_` 切分后含整词 `xp` / `experience`，如 `xp_fluid`、`flowing_xp_fluid`、
    `xp_still`、`liquid_experience`）；
  - 新增 `resolve()` 返回"命中原因"，供日志与命令解释。
- `config/XppConfig` + `config/XppSettings`：新增 `acceptExperienceNamedFluids`（默认 true）；默认
  `fluidConversions` 追加 `beyonddimensions:xp_fluid`、`sophisticatedcore:xp_still`（CEI 保留）。
- `command/XppCommands`：`/waystonexppayment info` 现在打印流体 id、命中原因与标签命中情况。
- 单测：`FluidRateTableTest` 11 → 17 例（互认、命名识别、子串不命中、可关闭、声明优先）。

## 为什么改

用户实测反馈两条：
1. **能从这里传出去，但传回这个罐体时仍要玩家自付经验**（经验不足就传不回来）。
2. **同为 `c:experience` 的经验流体，CEI 与超越维度的"不认"，精妙核心的可以；一旦罐里装过前者，连精妙核心的
   也不认了。**

第 1 条是设计缺口：原实现只认"来来源石碑下方"的罐，目标端有罐不参与支付。
第 2 条无法在离线复现，所以先查证据再改：
- CEI 2.5.4 的 jar 里**只有** `data/c/tags/fluid/dragon_breath.json`，**没有** `c:experience` 标签文件；
- 该整合包的 `kubejs/data/c/tags/fluid/experience.json`（`replace:false`）把 CEI 的两个 id 加入了 `c:experience`；
- `beyonddimensions` 自带 `c:experience`（`xp_fluid`、`flowing_xp_fluid`），`sophisticatedcore` 自带
  （`xp_still`）。三个文件都是 `replace:false`，按规则应取并集。

也就是说"按标签应该都能认"，但用户的观测不是这样，而我在本机无法运行该整合包验证标签真实内容。因此不再猜：
把识别做成**三条独立路径**（精确 id / 标签 / 命名启发式）+ **可自证的诊断输出**，让原因能在用户机器上一行命令
看到，而不是靠推测。

## 改动前后对比

| | 改动前 | 改动后 |
|---|---|---|
| 从有罐的石碑出发 | 罐支付 | 罐支付（不变） |
| 传送到有罐的石碑 | 玩家自付 | **罐支付**（目标端池子） |
| 流动/静流变体 | 只认声明的那一个 id | 互认（`flowing_` 前缀自动对应） |
| 未进 `c:experience` 的经验流体 | 不认（除非配置显式声明） | 命名含整词 `xp`/`experience` 即按 `mbPerXp` 认（可关） |
| 排查"为什么不认" | 只能猜 | `/waystonexppayment info` 输出流体 id + 命中原因 + 标签命中；接管成功时日志有 INFO 行 |

## 根因分析与教训

1. **"声明了标签" ≠ "运行时标签里真有它"**：CEI 在该版本根本没往 `c:experience` 里加自己，靠的是整合包 KubeJS
   补的标签；只要标签链任何一环没生效（KubeJS 数据包未加载、`replace` 冲突、标签命名空间不同），识别就会静默失败。
   对"用户体验为契约"的场景，应该有**不依赖单一标签**的兜底路径。
2. **静流/流动流是两个 id**：管道与桶灌进来的可能不是同一个变体。互认比让用户去查 id 更实际。
3. **不要在没有证据时给结论**：本轮先扫了三个模组 jar 的标签文件与整个实例的标签覆盖，才决定加哪几条路径；
   仍未复现的部分明确写成"本机无法验证"，并把可自证的诊断做进命令与日志。
4. **测试要跟着规则走**：新增命名启发式后，原单测里用 `some_mod:not_xp` 当"未声明流体"的样例恰好命中了新规则
   （`not` + `xp`），已改成 `some_mod:mana` 并补了"子串不命中"的用例，避免以后误判。
