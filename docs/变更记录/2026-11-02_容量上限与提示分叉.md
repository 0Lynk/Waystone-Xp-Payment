# 罐容量提到 16 桶，缺口提示分成两种说法

日期：2026-11-02
分支：`fix/tank-capacity-16`

## 改了什么

**一、把「罐付多付不起」的提示拆成两句**

`client/ClientFluidPaymentRequirement#appendHoverText` 原来只要罐付不起就打一句：

```
储罐只值 10 点经验，本次需要 27 点（还差 1700 mB）
```

这句话隐含一个前提：**把罐灌满就能补上缺口**。当 Waystones 的 `max_xp_cost` 被抬到超过「满罐价值」时，
这个前提不成立——罐已经装满了，再灌也补不上，提示会把玩家指向一个不可能完成的动作。

现在的判定（`payment/PoolQuote#topUpWouldCloseTheGap(int capacityMb)`）：缺口 mB 是否还在罐的剩余空间之内。

- 放得下 → 保留原话「还差 %s mB」；
- 放不下 → `gui.waystone_xp_payment.tank_short_of_reach`：「储罐最多只能付 %s 点经验，本次需要 %s 点；其余 %s 点要你自己付」。

容量从 `XpPaymentTankBlockEntity#capacityMb()` 取；远端罐（只有 hint、方块实体不在本地）拿不到容量时，
走第二句——那句话不需要容量就是对的。

**二、容量默认值与上限改为 16 桶**

`config/XppConfig.java`：

```java
.defineInRange("capacityMb", 16000, 1000, 16000);
```

原来是 `4000, 1000, 1_000_000`。默认值随之上调，上限从「1000 桶」收到「16 桶」。
理由（写进注释）：罐是钱包不是储物箱；10 XP/桶的廉价流体，16 桶 = 160 XP，
已经覆盖 Waystones 默认上限 27 XP 的六倍，再多只是让「一次灌满能走多远」失去意义。

## 为什么改

机主问「如果有人把 `max_xp_cost` 改到 40 以上会怎样」。算下来罐会从「钱包」退化成「补贴」：
100 点的票价，4 桶廉价流体最多出 40 点，剩下 60 点必须玩家自付。
这个行为本身是对的（`PoolQuote` 已经把缺口算给玩家），但提示仍按旧前提说话，会误导。

同时把容量提上去，让「满罐能覆盖任何一趟」在更大的票价区间里仍然成立。

## 改动前后对比

| 场景（10 XP/桶，罐 4000 mB 上限 27 XP） | 改动前 | 改动后 |
|---|---|---|
| 罐 1000 mB，票价 27 | 「还差 1700 mB」（可补满，正确） | 同左 |
| 罐 1000 mB，票价 60（管理员抬高了上限） | 「还差 5000 mB」——但罐只有 4000，补不上 | 「储罐最多只能付 10 点，本次需要 60 点；其余 50 点要你自己付」 |
| 新放置的罐 | 4000 mB | 16000 mB |
| 已有存档里的罐 | 4000 mB | 方块实体重建时按配置取值（重进世界/重启后为 16000） |
| 已有配置文件里的 `capacityMb` | 4000 | **仍是 4000**——新的默认值不会覆盖已写进文件的旧值，见下节 |

## 备选方案

- **a. 只改容量，不改提示**：票价上限一旦被抬到 160 以上，提示依然会说「还差 N mB」，把玩家送去灌一个已经满的罐。
- **b. 只改提示，不改容量**：改动最小，但「满罐也付不起」的区间会停留在 40 XP 以上，比 16 桶窄得多。
- **c. 在提示里同时给出「补罐」和「自付」两条路**：信息更全，但两句话在 3 秒的悬停里读不完，且多数情况只有一条路可行。

选 a 的反面 + b 的反面：两件事一起做，提示按「能不能补上」分流，容量给到一个仍然合理的余量。

## 意外点

1. `capacityMb()` 必须读 `tank.getCapacity()` 而不是配置项：方块实体是拿构造时的容量建的，配置项在它建好之后可能已经被改过。
   但**容量本身不存 NBT**，所以「旧罐永远是旧容量」只在同一次会话里成立——重进世界它就按新配置重建了（见「已知限制」）。
2. 远端罐没有容量可用，所以第二句的措辞不能出现 mB 或容量，否则又会变成一句不一定成立的话。
3. 上限收到 16000 是一次**向下的收窄**：原先允许到 1,000,000 mB 的管理员配置现在会被夹到 16000。配置文件里已有的更大值会在加载时被 NeoForge 纠正并告警。

## 验证

- `.\gradlew.bat test --offline` → **26 suites / 165 tests / 0 failures**（162 → 165，`PoolQuoteTest` 新增 3 例）。
- 负向验证：把 `topUpWouldCloseTheGap` 改成恒 `true` → `aGapBeyondTheFreeRoomIsNotWorthFilling`（`PoolQuoteTest.java:112`）与
  `aFullTankCannotAbsorbAnything`（`:121`）两例变红，还原后全绿。
- 未覆盖：`appendHoverText` 的分支需要客户端 `Player` 与 `XpPaymentTankBlockEntity`，测试类路径里没有，靠实机冒烟与目视。

## 已知限制

- **改默认值不会改动已经存在的配置文件**：NeoForge 只在键缺失时才写入默认值，所以装过旧版本的实例里 `waystone_xp_payment-common.toml`
  仍是 `capacityMb = 4000`，罐也就还是 4 桶。要么手改这一行，要么删掉配置文件让它按新默认值重建。
- 容量在方块实体构造时从配置读取（`XpPaymentTankBlockEntity.java:68`），NBT 里只存流体与访问列表，**不存容量**。
  因此同一个会话里已经实例化的罐保持旧值，重进世界或重启服务端后按新配置重建；罐里已有的流体会原样保留（容量变大时不会截断）。
- `describeAffordability()` 的日志行仍用 mB 描述缺口（诊断用，不含「灌满即可」的暗示）。
