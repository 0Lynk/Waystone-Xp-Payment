# 置灰归属的两处误判（站在上面的那个石碑、创造模式）— 2026-10-24

## 为什么改

机主问：「此修复会造成负面影响吗？」把 Waystones 侧「谁会把 `active` 置 false」穷举了一遍（`javap -p -c` 反编译
`WaystoneButton` 构造器 + `WaystoneList$WaystoneEntry` 构造器，再全 jar 扫 `putfield active:Z`），只有三处：

1. `WaystoneButton` 构造器：`Minecraft.player == null`。
2. `WaystoneButton` 构造器：`!warpRequirement.canAfford(player)` **且** `!player.getAbilities().instabuild`。
3. `WaystoneList$WaystoneEntry` 构造器：该条目的 `waystoneUid` 等于来源石碑（就是你正站着的那个）。

第 1 条走不到（mixin 里 `player == null` 已经直接 return）。第 2、3 条正是上一轮那一版会误判的两种：

- 第 3 条：站在石碑上时列表里「当前位置」那一行本来由 Waystones 置灰，而上一版 `PaymentGreyState` 的首帧规则
  `ownedByPayment = !affordable || activeNow` 会把「付不起且已灰」认成自己的灰，罐补满后把按钮点亮，等于允许
  传送到自己脚下。
- 第 2 条的后半段 `instabuild`：Waystones 在创造模式刻意不置灰（免费传送），而我们的 `canAfford` 只看罐和玩家经验，
  创造模式玩家经验为 0 时会把条目打灰——服务端在创造模式根本不收费，属误伤。

两种都会在「界面开着、罐被补满」时把按钮从灰变亮，正是上一轮修复引入的新可达路径，因此必须堵。

## 备选方案与取舍

- **在 `PaymentGreyState` 里加「当前石碑」特判**：需要在 mixin 里拿到 `fromWaystone`，而 mixin 只注入按钮自身，
  信息不够；硬塞进去要新的 `@Shadow` 或线程本地上下文，比在 `decorate` 一处早退复杂得多。不选。
- **让 `canAfford` 直接读 `instabuild` 而不看配置**：创造模式也受服务端配置控制，服务端关掉 `skipPaymentInCreative`
  时仍然收费，客户端若无条件放行就会「亮着但点了被拒」。选「跟配置走」，配置偏差只导致一次被拒的点击，不会卡住按钮。
- **只做创造模式、不动自目标**：自目标那条更常见（列表第一行永远是当前位置），留着会让「点亮自己」成为一个可复现的
  怪行为。两条一起做。
- **什么都不改，只回答「没有负面影响」**：不诚实——`putfield active:Z` 的穷举已经证明确有两条可达路径。

## 意外点

- `WaystoneEntry` 用 uid 判等来置灰「当前石碑」（`waystone.getWaystoneUid().equals(fromWaystone.getWaystoneUid())`），
  说明 Waystones 自己也把「传送到自己」当成无意义操作；我们的预览之前没跟上这条语义。
- `decorate` 里 `getTargetWaystone()` 没有 `Optional` 包装，理论上可为 null；新加的 `waystoneUid(...)` 顺带补上了这个
  空值边界（`tankBelow` 早就有 null 判，说明这条路径不是不可能）。
- 创造模式的放行只在客户端预览层：服务端 `event/XppTeleportHandler` 本来就有 `skipPaymentInCreative` 分支，两端口径一致。
- 仍存的风险（**未改**）：池量恰好在总价附近来回震荡时，按钮会随之前后翻转，每次翻转打一行 INFO。翻转由罐内流体变化
  驱动，正常运行（一次抽干或一次补满）只会翻一次；只有在阈值上反复灌/抽的极端测试里才可能刷屏。要压掉得在 mixin 里加
  时间戳节流，属另一件小事。
