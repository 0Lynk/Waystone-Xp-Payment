# 2026-10-10 客户端判定不再依赖同步快照（修"换回可用流体也没用"）

## 改了什么

- `client/ClientFluidPaymentRequirement`：不再读取罐子的同步池值；只校验"除 XP 花费之外"的其它需求
  （冷却、物品等）是否满足，XP 部分交给服务端裁决。
- `client/XppClientRequirements`：套用条件降为"**来源或目标石碑正下方存在本模组的罐**"，不再看罐里有什么。
- `event/XppTeleportHandler`：当选中的罐当前无法支付（`poolXp() <= 0`）时，打印一条 WARN 说明罐在哪个位置、
  里面是什么流体、为什么无法支付（附 `/waystonexppayment info` 同款描述文本）。
- 重新构建并覆盖到测试实例（94,137 字节，2026-10-10 22:40:06）。

## 为什么改

用户指出真正的 bug（我上一轮把它误判成"单流体罐的设计限制"，不对）：

> 既然它不认……那么它应该放不进去，就和水和岩浆的逻辑一样，既然放进去了它就应该认。
> 而且如果里面放进去的流体它没有认过，即使把这些流体取出来、再放入原本可用的经验流体，它依然会无法使用。

第二句是决定性的：**罐子被"毒化"了且永久不恢复**。根因在客户端：

- 上一版客户端按钮判定读的是方块实体同步来的 `XppPoolXp`（服务端算好的池值）；
- 该值一旦是 0（罐里是不被承认的流体），或该同步包因任何原因没到/过期，客户端就**一直**认为池子为 0；
- 换回可用流体后，服务端其实已经能正常支付（服务端是每次现算的），但**玩家连按钮都点不动**，于是表现为"永远不认"。

也就是说：这不是流体识别问题，而是**客户端把一次同步值当成了长期事实**。

## 改动前后对比

| | 改动前 | 改动后 |
|---|---|---|
| 客户端可点性判定依据 | 同步快照里的池值 | 只看"两端任一方块下有没有罐" |
| 罐里是不被承认的流体 | 客户端永久灰按钮（毒化） | 按钮可点；服务端按实际流体决定，付不了则给 NotEnoughXp |
| 罐里换成可用流体 | 依然是灰的 | 立即恢复正常 |
| 诊断 | 无 | 罐无法支付时 WARN 一行：位置 + 流体 + 无法支付原因 |
| 插入与支付是否同一判定 | 是（同一函数） | 是（不变）——所以"能灌就能用，不能灌就灌不进去" |

## 根因分析与教训

1. **权威方与判定方必须分清**：服务端是唯一权威（每次现算），客户端只是"预览"。让预览依赖一个可能过期的
   同步值，就会产生"服务端明明可以、客户端却永久锁死"这类顽固 bug。预览的判定条件应当是**稳定的结构事实**
   （这里：罐是否存在），而不是易变的数值。
2. **"毒化"类 bug 的共同形态是缓存了不该缓存的状态**：本轮把它定位到"客户端缓存了池值"，修法是删掉这条
   依赖，而不是再加一层刷新逻辑。
3. **同一次判定只应有一个函数**：`FluidTank.isFluidValid` 与支付用的都是 `FluidRates.rateFor`，所以
   "放得进去 = 认" 在设计上成立；用户看到的不一致来自客户端预览，而不是两条不同的服务端规则。
