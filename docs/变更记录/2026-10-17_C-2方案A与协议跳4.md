## 为什么改

上一轮（远端目的地罐）把"未加载区块的罐"这条路径做通了，但它只回答了"那里有多少 XP"，没回答"**你**能不能用"。
证据：`net/XppServerHandler#hintFor` 不接收玩家，直接读罐的池量。后果有两个，都已在线上：

1. **假阳性**：没有授权的玩家，按钮按罐主的池量点亮 → 点下去服务端拒绝 → 回退玩家付 XP → 付不起就传送失败；
2. **池量泄露**：任何人对任何位置（≤32 槽/包、任意距离）都能问出罐主的库存。

同时，模式 (`whitelist`/`blacklist`) 是靠 `label` 里的字符串传输的，改写或翻译这句显示文本就会翻转一条权限规则。

## 与上一版的对比

| | 上一版 | 本版 |
|---|---|---|
| 提示包 | `{pos, poolXp, mbPerXp}` | `{pos, poolXp, mbPerXp, access}` |
| 未加载 + 索引无记录 | `UNKNOWN` 池量（客户端保守放行） | 同左，且 `access = UNKNOWN` |
| 开关关闭 | 回 `NO_TANK`（"这里没罐"——假话） | 回 `UNKNOWN`（"我不知道"） |
| 未授权 | 与有授权**无法区分** | `DENIED`，不报池量，客户端不当作付款方 |
| 模式 | `label` 里的 `"whitelist"/"blacklist"` | 专用 `Mode` 字段 |
| 协议 | `3`（裸字面量） | `4`（`PROTOCOL_VERSION` 常量） |

## 根因

三处属于同一类：**让客户端在没有数据的情况下自己补答案**。授权、池量、模式都是"服务端才知道的事"，
却被编码进"客户端能自己算"的形状里；一旦数据不在本地，客户端就只能猜，猜错就变成报价撒谎或越权。
本版的做法统一为：服务端回答"能不能用 + 多少"，客户端只负责显示与算术，不再自行推断。
