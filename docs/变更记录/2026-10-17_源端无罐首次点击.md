# 源端无罐时第一次点击必失败

- 状态：PENDING VERIFICATION（单测与构建通过，实机未复测）
- 分支：`fix/source-slot-load-budget`
- 日期：2026-10-17

## 改了什么

`event/XppTeleportHandler#tankBelow` 不再对「区块已经在内存里」的候选申请区块加载配额：

```java
// 之前：先把配额花掉，再去看有没有罐
if (!budget.requestLoad(key, now, REMOTE_PAYER_MEMO_MILLIS)) {
    return resident;
}
level.getChunk(...);

// 现在：只有「没读到罐、且区块确实不在内存里」才花配额
if (!shouldLoadForTank(resident != null, level.isLoaded(waystonePos))) {
    return resident;
}
if (!budget.requestLoad(key, now, REMOTE_PAYER_MEMO_MILLIS)) {
    return resident;
}
```

新增包级纯函数 `static boolean shouldLoadForTank(boolean tankFoundHere, boolean chunkResident)`，
判定从 IO 里拆出来，好让「驻留区块不花配额」这件事有单测。

## 为什么改

机主报的现象：源传送点没有罐、目的地有罐时，**第一次**点击目的地必然失败，**第二次**成功。

`payment/PayerBudget#requestLoad` 的契约是「本次传送允许加载几块区块」，它只数次数，不看那块区块
现在是否已经在内存里——只要 `used < chunkLoads` 就 `used++`。一次传送里 `XppTeleportHandler`
先探源端再探目的地，而源端石碑永远驻留（玩家就站在那儿），源端又常常没罐。于是：

1. 源端没有罐 → 仍然问配额 → 默认的 1 份配额（`XppSettings.DEFAULTS` 的
   `remotePaymentChunkLoads = 1`）被这一问花掉；
2. 目的地真的需要加载 → `requestLoad` 返回 `false` → 没有付款方 → 回退玩家自付 → 失败；
3. 5 秒内第二次点击命中 `PayerBudget.RECENT_ATTEMPTS` 的记忆，源端不再问配额，
   目的地这才会拿到那 1 份 → 成功。

「第一次必失败、第二次成功」的稳定性正是第 3 步造成的假象：它不是重试变好了，而是防抖替源端省下了配额。

## 备选方案

1. **调换探测顺序**（先目的地后源端）：治标。付款方的选择本来就是「源端优先」，换顺序会改变语义，
   而且任何一次两端都要问配额的传送仍会退化成同一个 bug。
2. **给 `requestLoad` 加一个 `resident` 参数**：让预算类知道区块状态，等于把调用方的知识塞进纯计数器，
   还会让「加载了几块区块」不再能从计数推出来。
3. **在调用侧判断**（本方案）：配额只在真的需要加载时才花；`PayerBudget` 保持「只数次数」的单一职责。

## 意外点

源端驻留这件事不是特例而是常态——玩家必须先站在源端石碑上才能传送。所以这 1 份配额在
「源端无罐」的传送里从第一步起就没有意义，`requestLoad` 的 `used++` 只是在记「问过几次」，
而不是「加载过几次」。这层错配在只有目的地会真正加载区块的架构下，等于把默认配额净减 1。

## 风险与未覆盖

- **实机未验**：需要在客户端跑一次「源端无罐 → 点有罐的目的地」，确认第一次点击就由目的地罐付款。
- 只在默认配置（`remotePaymentChunkLoads = 1`）下推理过；配额 ≥ 2 时现象会被掩盖，但浪费仍然存在。
- 没有把「两端都要加载区块」的场景做成端到端测试——那需要 `ServerLevel`，单测只覆盖判定本身。
