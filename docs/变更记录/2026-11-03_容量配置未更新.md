# 容量默认值改了，但旧配置文件没改

日期：2026-11-03
分支：`docs/capacity-config-note`

## 改了什么

只改文档，不动代码。修正三处不准确的说法，并新增一条给使用者看的操作说明。

1. `CHANGELOG.md`：把「Tanks already placed keep the capacity they were built with; break and replace one to grow
   it」改成「已经存在的配置文件不会被新默认值覆盖，请自己改成 `capacityMb = 16000`；容量不写进存档，方块实体
   重建（重进世界/重启）时按配置取值，罐内流体保留」。
2. `README.md` 配置示例那一行的注释：从「existing tanks keep their old capacity」改成「existing config files keep
   whatever they already say」。
3. `docs/变更记录/2026-11-02_容量上限与提示分叉.md`：对比表新增一行「已有配置文件里的 `capacityMb`」，改写「已知限制」
   与「意外点 1」。
4. `docs/问题修复清单.md` 第十三轮表格与待验证清单同步。

## 为什么改

机主报告「储罐的容量没变，还是 4 桶」。查下来是**两件事叠在一起**，而文档只写了其中一件：

- 六个测试实例的 `waystone_xp_payment-common.toml` 里都是 `capacityMb = 4000`。NeoForge 只在键缺失时写入默认值，
  已经有值的键**永远不会**被新的 `defineInRange` 默认值覆盖，所以 `16000` 这个新默认值只对全新安装生效。
- 容量不在 NBT 里（`block/entity/XpPaymentTankBlockEntity.java:68` 在构造器里读配置，`saveAdditional` 只写流体与
  访问列表），所以「旧罐永远 4 桶」只在同一次会话里成立；重进世界会按新配置重建。

我上一轮写的「要 16 桶需拆掉重放」因此是错的：真正需要改的是配置文件，不是方块。

## 改动前后对比

| 说法 | 改动前 | 改动后 |
|---|---|---|
| 旧罐怎么变成 16 桶 | 「拆掉重放」 | 「改配置文件的 `capacityMb`，然后重进世界/重启」 |
| 新默认值的作用范围 | 隐含「装上新版就生效」 | 明说「只对全新配置文件生效，旧文件保持原值」 |
| 容量存在哪里 | 未说明 | 明说「不存 NBT，构造时读配置」 |

## 备选方案

- **a. 让 mod 自动把 4000 升级成 16000**：分不清「旧默认值」和「管理员故意设成 4000」，会自动改掉别人的选择，否决。
- **b. 启动时打印一行生效容量**：能减少下一次的困惑，但属于代码改动，要连带发布，留作可选。
- **c. 只改这一处描述，其余不动**：会让 CHANGELOG 与变更记录继续互相矛盾。

选 c 的反面：四处口径一起改，并把「配置不会自动更新」这条**前置条件**写进入门位置（CHANGELOG 与变更记录）。

## 意外点

1. 真正的触发器不是「方块已经放下」，而是「配置文件里已经存在这个键」。前者只影响当前会话，后者是永久的。
2. 反过来把容量调小时，`XpPaymentTankBlockEntity` 的 `clampLoadedPoolToCapacity()` 会把超出的流体截掉——
   往大调没有这个副作用，所以本轮的改动本身不丢东西。
3. 六个测试实例的配置文件已经按本结论手动改成 16000（`D:\Minecraft\重度机霸症Server\config`、
   ShatteredPrism 三实例、PrismLauncher 两实例）。

## 验证

- 文档改动，无代码变更；`gradlew test` 与 jar 均不受影响（最近一次全量结果仍为 26 suites / 165 tests / 0 failures）。
- 已核对六个实例的配置文件当前均为 `capacityMb = 16000`。

## 已知限制

- 玩家侧仍需要重启客户端/服务端，配置才进入 `XppSettings`；同一会话里已经加载过的罐不会变。
