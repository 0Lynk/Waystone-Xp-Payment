# 语言约定：文档中文、代码与 git 历史英文

日期：2026-10-30
分支：`docs/language-policy`
相关提交：本文件所在提交

## 改了什么

1. `AGENTS.md`
   - 「## 代码风格 → 禁止」清单里删掉最后一条「把中文注释改写成英文」——它和这次要立的规则直接冲突，且当时并没有对应的英文规则存在。
   - 新增「## 语言约定」小节：文档用中文（`docs/` 的正文、文件名、目录名，以及本文件）；git 历史用英文（commit message、PR 标题与正文）；代码用英文（包名、类名、字段名、局部变量、注释、javadoc，以及 `src/` 下的文件名与目录名）；例外只有 `src/main/resources/assets/waystone_xp_payment/lang/*.json`。
   - 该文件此前**未被 git 跟踪**，这次一并入库，规则才会跟着仓库走、而不是只存在于本机。
2. 新增 `.github/PULL_REQUEST_TEMPLATE.md`（英文）：把「commit 与本说明英文、`src/` 下的新路径英文、文档保持中文」做成提交前的勾选项。
3. 新增 `.github/scripts/check-language.py`：扫描受跟踪文件里被检查路径（`src/`、`tools/`、`gradle/`、`.github/` 以及根部的构建文件）是否含 CJK，并扫描给定提交区间内每条 commit 的标题与正文。
4. `.github/workflows/build.yml` 新增 `language` job：`fetch-depth: 0` 检出后调用上面的脚本。PR 事件用 `github.event.pull_request.base.sha..HEAD`，push 事件用 `github.event.before..HEAD`（全零时不查提交、只查路径），`workflow_dispatch` 只查路径。

没有改动任何源码、资源、协议或构建产物。

## 为什么改

盘点结果（148 个受跟踪文件）：

| 区域 | 现状 |
|------|------|
| `src/` 下 72 个 Java 文件 | 注释与 javadoc **全部英文**，标识符全英文，文件名全英文 |
| `docs/` 下 51 篇 | 正文全中文，文件名/目录名中文（49 个中文文件名 + 2 个中文目录） |
| `README.md`、`CHANGELOG.md`、`build.gradle`、`.github/` | 全英文 |
| 50 条 commit | 14 条中文标题 + 14 条中文正文，集中在 10-11～10-24；其余 36 条英文 |

也就是说，中英混用不在同一个文件内部，而在**同一仓库的不同通道**：代码与 README 英文，文档与部分提交中文，且没有任何一份文件说明「哪一块该用哪种语言」。结果是同一个 PR 里中文正文配英文方案、中文变更记录配英文 commit，读的人要来回切换，写的人每次都要猜。

口头约定解决不了这个问题：这个仓库的每一轮改动都由新的会话完成，规则只要不在自动加载的文件里，两三轮之后就会被忘掉。所以规则写进 `AGENTS.md`（每个会话自动加载），再由 CI 兜底。

## 备选方案与取舍

- **a) 整个仓库英文化**（把 51 篇文档、49 个文件名、历史提交说明都翻成英文，约 7–8 人日）：机主明确要求文档保持中文，否决。文档是给中文使用者看的，翻译反而降低可读性。
- **b) 只写规则、不加 CI 检查**：改动最小，但规则没有任何反面代价——写错了照样能合并，下一轮就可能重新混入。否决。
- **c) 在 Gradle 里加一个 `checkLanguage` 任务**：能跟着 `gradlew build` 一起跑，但要读 git 上下文、且让每次本地构建都依赖 git 状态；CI 里已有的 `build` job 也会因此变慢。否决，改为独立的 `language` job。
- **d) 选中的方案**：规则写进 `AGENTS.md`，PR 模板做人工提醒，CI 脚本做机器检查。检查脚本是纯 Python、无第三方依赖，本地可以用 `python .github/scripts/check-language.py --range <a..b>` 复现 CI 的判定。

## 意外点

1. `git ls-files` 默认开 `core.quotepath`，中文文件名会以八进制转义返回（`\344\270\255…`），正则匹配不到。脚本里显式传 `-c core.quotepath=false`，否则这条检查就是空转——一个永远通过、看起来却很像在工作的检查比没有检查更危险。
2. 历史上 14 条中文 commit 不回改：改写要 force-push 主干，而 `rebase` 合并已经把它们的正文写进了 main 的历史。规则只能向前生效，这一点写进了 `AGENTS.md`，避免以后有人以为「规则立了就该把历史也清干净」。
3. 只检查 `src/`、`tools/`、`gradle/`、`.github/` 和根部构建文件，不检查 `docs/`：文档按约定就是中文，若一并检查，脚本永远报错，规则就废了。
4. 提交正文的检查按行报错，一条 commit 只报第一行命中——避免一个中文段落刷出几十行。

## 验证

1. `python .github/scripts/check-language.py --paths-only` → `language policy holds for source paths`，退出码 0（现有 `src/` 无中文路径）。
2. `python .github/scripts/check-language.py --range 4a8546e~1..4a8546e`（英文提交区间）→ 退出码 0。
3. `python .github/scripts/check-language.py --range 5399b05~1..5399b05`（历史中文提交）→ 退出码 1，逐条列出 `commit 5399b05c4f48 has a non-English subject: docs: …` 与正文命中行 —— 检查确实会拦。
4. 未改源码：`git diff --stat` 仅含 `AGENTS.md`、`.github/`、本文件；jar 与测试数不变，无需重新构建、无需重新部署五个测试实例。

## 未覆盖

- CI 里的 `language` job 只能在本仓库跑通后才算验证；本地脚本逻辑已验证，GHA 侧的 `RANGE_START` 表达式（`pull_request.base.sha` 与 `push.before` 二选一）需要推送后看一次真实运行结果。
- 代码注释的英文要求靠人工与评审，没有机器检查（扫注释会误伤 `lang/*.json` 之外的字符串常量）。
