## 为什么改

机主复测第五轮修复后反馈：「还是会偶尔失败，但是概率小多了」。

问诊得到两个关键细节：

1. 失败时客户端给出了红字提示（经验不足一类的「付不起」文案）；
2. **第二次点击在 1 秒内就成功**。

第 2 点直接排除了防抖记忆本体：如果失败是记忆造成的，1 秒内重试仍然会命中记忆，不可能成功。于是问题
不是「记忆太长」，而是「记忆记错了对象」——它记下的是**成功**。

## 改动前后对比

```java
// 之前：每一次放行都写记忆，包括加载成功、罐就在那儿的那次
public boolean requestLoad(String slot, long nowMillis, long memoMillis) {
    if (recentlyTried(slot, nowMillis)) return false;
    if (used >= chunkLoads) return false;
    used++;
    rememberUntil(slot, nowMillis + memoMillis);   // ← 祸根
    return true;
}

// 之后：放行不记，只有「加载了却没读出罐」才记
public boolean requestLoad(String slot, long nowMillis) { ... used++; return true; }

public void rememberMiss(String slot, long nowMillis, long memoMillis) {
    rememberUntil(slot, nowMillis + Math.max(0L, memoMillis));
}
```

## 根因分析

`PayerBudget` 的记忆本意是「这块区块刚看过，里面没有罐，别为了同一个空结果反复把它拉进来」。但写入点
放在 `requestLoad` 的放行分支上，而放行分支无法区分「加载后有没有读到罐」。

后果链：

1. 玩家第一次去目的地 D，目的地区块不在内存 → 申请配额 → 放行 → **写入 D 的记忆 5 秒** → 加载 → 读到罐 → 由罐付款成功；
2. 玩家传送离开，目的地 D 的区块在停留时间过后被卸载（目的地本来就不是玩家久留的地方）；
3. 5 秒内玩家再点 D（连续跑图、来回试目的地是常见操作）→ `requestLoad` 命中记忆 → 拒绝加载 → 无付款方 → 回退玩家自付；
4. 玩家经验不够付这一趟 → 红字「付不起」 → 一秒后重试时记忆已过期 → 由罐付款成功。

界面预览**不走**这条路径：`net/XppServerHandler#hintFor` 与客户端提示缓存（`XppTankHints`）既不会读
`PayerBudget`，也不会加载区块；收到 `UNKNOWN` / `NO_TANK` 时客户端按玩家 XP 决定按钮是否点亮。所以
「按钮亮着却付不起」与预览无关，排查时要分开看这两条链。

旧 javadoc 其实已经写着「A granted load normally leaves the chunk resident, so the next click on the same
entry takes the already-loaded path and never comes back here; the memo therefore only matters for the failure
case」——那段话假设了「加载成功后区块会一直驻留」，对源端（玩家站着不走）成立，对目的地恰恰不成立。
注释描述的是一个不存在的世界，代码照它写，于是成功被当成了失败。

## 风险与未覆盖

- **未验**：实机上需要「5 秒内连续两次去同一目的地」，两次都应由目的地罐付款（这是本轮唯一的验收动作）。
- 失手抑制行为未变：真正没罐的位置依然是 5 秒内只尝试一次，连点不会把区块反复拉进来。
- `REMOTE_PAYER_MEMO_MILLIS` 仍是 5 秒常量；如果后续出现「目的地罐确实存在但第一次预览不到」的另一类
  现象，需要另查客户端提示缓存（`XppTankHints` 的 30 秒 TTL），与本轮无关。
