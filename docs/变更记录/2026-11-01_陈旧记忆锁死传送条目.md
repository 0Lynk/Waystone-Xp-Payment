# 传送到未加载区块、下方有罐的石碑时按钮永久灰

2026-11-01

## 改了什么

1. `src/main/java/com/olynk/waystonexppayment/client/XppClientRequirements.java`
   - `selectPayerSlot(...)`：第一轮「客户端自己见过这个槽位有罐」不再无条件胜出，加一个否决条件——服务端已经明确回答
     「这个槽位不能付款」（`Hint.none` 的 `NO_TANK`，或 `Hint.denied`）时，记忆让位，继续看下一轮「哪个槽位真的付得起」。
   - `readableTank(...)` / `isReadable(...)`：远端槽位只要服务端的最后一次回答说「这里确实有罐」（`hint.hasTank()`），
     也允许包装成付款预览；不再是「只认本客户端已加载的罐」。
   - `describeTank(...)`：诊断日志从「tank not loaded here」升级为
     `unloaded slot at 35, 64, 28 (server says 60 XP)` / `(server says no tank)` / `(no answer yet)` / `(server says denied)`。
2. `src/test/java/com/olynk/waystonexppayment/client/XppClientRequirementsTest.java`：新增 3 例
   `aRememberedSlotTheServerSaysIsEmptyIsStillTheTank`、`aRememberedSlotTheServerSaysHasNoTankYieldsToThePayingSibling`、
   `aRememberedSlotThisPlayerMayNotUseYieldsToThePayingSibling`，并改写类 javadoc 的两句口径。

## 为什么改

现场：用传送石/传送卷轴（`from=none`）传送到未加载区块里的石碑 `35, 66, 28`，它下方 `35, 64, 28` 有 60 XP 的罐，
但列表里那一行是灰的，重开列表也不亮。客户端日志：

```
[client] no payment tank for this entry (from=none, target=minecraft:overworld@35, 66, 28):
         under source=no tank, under target=tank not loaded here
```

`35, 66, 28` 未加载，`TankPlacement` 只能给出两个候选：`35, 65, 28` 与 `35, 64, 28`。服务端索引里
`35, 65, 28 = NO_TANK`、`35, 64, 28 = 60 XP`（`milliXpPerBucket = 10000`，10 XP/桶）。

旧逻辑的两层问题叠在一起：

- `selectPayerSlot` 的第一轮是「客户端记住过哪个槽位有罐」，它先于「服务端说哪个槽位付得起」，而且**不与服务端的回答对账**。
  只要客户端曾经在 `35, 65, 28` 这个槽位见过罐（罐子后来下移一格、或拆掉重建），这个陈旧记忆就会一直被选中。
- 选中之后 `payerAt(...)` 才发现服务端对这个槽位说的是 `NO_TANK`，于是返回 `null`；`readableTank(...)` 只接受**已加载**的罐，
  远端槽位一律不接，于是 `decorate` 走进 `no payment tank` 分支返回原始 requirement。
- 返回原始 requirement 的后果比「这一帧灰」严重得多：每帧刷新只作用于被我们包装过的条目，条目一旦没被包装，
  **整个会话都不会再变**——这正是「关闭界面刷新也不能点亮」。

## 改动前后对比

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 记住的槽位被服务端回答 `NO_TANK`，另一个候选付得起 | 选中记忆槽位 → `payerAt` 拒绝 → 原始 requirement → 永久灰 | 记忆被否决 → 选中付得起的候选 → 正常包装、正常亮 |
| 记住的槽位被服务端回答 `DENIED`（罐是别人的） | 同上，永久灰 | 让位给另一个候选 |
| 记住的槽位服务端说「有罐但空」 | 选中记忆槽位 → 池 0 → 灰（可恢复） | 同左（空罐仍算罐，补液后逐帧刷新会亮） |
| 远端罐上次回答 60 XP，本次未加载 | 只有已加载才算可读 → 不包装 | 允许包装，池量来自 hint 并每 5 秒重问 |

## 根因分析

不是渲染问题，是**证据等级弄反了**：`XppClientTankRegistry` 记的是「这个坐标上曾经有过一个罐」，这是关于**位置**的记忆；
`XppTankHints` 记的是「服务端刚才说的这个坐标付不付得起」，这是关于**当前状态**的答案。旧实现把位置记忆当成状态答案，
于是「罐挪了一格」这种再普通不过的改动能把一整行永久锁死。

`readableTank` 只认已加载的罐，则来自更早一版的设计：那时远端 hint 只在构建条目时刷新一次，包装它没有意义。
后来 `ClientFluidPaymentRequirement.hint()` 每帧会调 `XppTankHints.refreshIfStale(...)`，这个前提已经不成立，注释与实现脱节。

## 备选方案

- a) 只在 `decorate` 里兜底：`payerAt` 返回 null 时改用另一个候选。治的是症状，`selectPayerSlot` 依旧会选错槽位，
      旧记忆会持续污染工具提示里的池量数字。
- b) 让 `XppClientTankRegistry` 支持「忘记」某个槽位（收到 `NO_TANK` 就删）。会引入客户端状态与服务端答案的同步问题，
      并且没解决「记忆先于答案」这个次序错误。
- c) 选中槽位改名换姓、不加否决条件，只把 `readableTank` 放宽。远端槽位被选中后仍然是 `NO_TANK`，依旧灰。
- **采用**：在 `selectPayerSlot` 里加否决条件（记忆与答案对账），并同步放宽 `readableTank`。

## 意外点

- `Hint.mayPay()` 已经同时排除了 `NO_TANK` 与 `DENIED`，所以否决条件写成一个表达式就够，不需要分别判断两种拒绝。
- 放空罐也算「记忆有效」，是因为空罐可以补液，而补液后每帧刷新能把行点亮；真正该让位的只有「这里没有罐 / 你不能用」。

## 验证

- `.\gradlew.bat test --offline` → 30 suites / 185 tests / 0 failures（182 → 185）。
- 负向验证：把第一轮改回无条件的 `if (seenHere.test(candidate))` →
  `aRememberedSlotTheServerSaysHasNoTankYieldsToThePayingSibling`（`XppClientRequirementsTest.java:66`）与
  `aRememberedSlotThisPlayerMayNotUseYieldsToThePayingSibling`（`:74`）同时变红；还原后全绿。
- 未覆盖：`readableTank` 的放宽需要客户端 `Level` 与真实 hint 缓存，`decorate` 这条路径仍无单测（测试类路径里没有客户端世界）。

## 待实机验证

1. 站在传送石或拿传送卷轴，选一个「没去过、区块未加载、下方有罐」的石碑 → 行应亮，悬停显示「储罐可付 X 点经验」。
2. 把罐子从 `y-1` 挪到 `y-2`（或拆掉重放），不重启客户端 → 行应在一两秒内恢复，而不是整局灰着。
3. 罐里留 0 mB → 行应先灰；用泵灌到够这次票价 → 行应自己亮起来。
