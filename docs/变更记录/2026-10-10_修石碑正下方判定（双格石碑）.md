# 2026-10-10 修"石碑正下方"判定（双格石碑）

## 改了什么

- 新增 `payment/TankPlacement.tankPosFor(Level, Waystone)`：从 `waystone.getPos()` 起，**若其正下方是同一个石碑方块**（即该石碑是 `DoubleBlockHalf` 双格结构、记录坐标落在上半格），则罐位再往下取一格；否则就是 `pos.below()`。
- `event/XppTeleportHandler.payerAt` 与 `client/XppClientRequirements.tankBelow` 都改用该函数（服务端与客户端判定必须一致，否则会出现"能点但服务端不付"或反之）。
- 重建并覆盖到测试实例（见回复中的字节数与时间）。

## 为什么改

用户指出（我此前的判断是错的）：**Waystones 的石碑是两格高的方块**。他的罐在 `(19,-60,8)`、日志里石碑坐标是 `(19,-58,8)` —— 我据此认为"相差两格、不紧贴"，但石碑占 `(19,-58,8)` 与 `(19,-59,8)` **(19,-59,8) 是它的下半格**，罐在 `-60` 正好是**紧贴石碑最下面那格的下方**，摆法本来就是对的；错的是我的 `getPos().below()`。

源码验证（`D:\deepseek\_ref\Waystones\...`）：
- `block/WaystoneBlockBase.java:88-102`：`state.hasProperty(HALF)`、`DoubleBlockHalf half = ... state.getValue(HALF)`、`BlockPos offset = half == DoubleBlockHalf.LOWER ? pos.above() : pos.below();` → 石碑确实是双格方块；
- `block/WarpPortalBlock.java:69`：`final var basePos = state.getValue(HALF) == DoubleBlockHalf.UPPER ? pos.below() : pos;` → 不同传送源的"规范坐标"可能落在上半格或下半格**并不统一**。

因此不能固定用 `pos.below()`，而应按**方块状态**向下找：下方是同一方块 → 继续向下 → 取最低格的下方。

## 改动前后对比

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 单格来源（传送板/传送石等） | `pos.below()` ✅ | 不变 ✅ |
| 双格石碑，记录坐标在下半格 | `pos.below()` ✅ | 不变 ✅ |
| **双格石碑，记录坐标在上半格** | `pos.below()` 指向石碑自己的下半格 → 永远找不到罐 ❌ | 取最低格的下方 ✅（用户当前摆法即可用） |
| 服务端/客户端一致性 | 两处各写一遍 `pos.below()` | 共用 `TankPlacement`，不会再各改一处 |

## 根因分析与教训

1. **多格方块不能只按"坐标 ±1"推理**：方块记录的坐标未必是它的"脚底"，必须查方块状态（这里是 `DoubleBlockHalf`）。
2. **同一判定不要在两处各写一遍**：服务端与客户端原本各写 `waystone.getPos().below()`，改一处漏一处就会立刻产生"客户端放行/服务端不付"的分裂。本轮抽成 `TankPlacement` 共用。
3. **用户的世界证据优先于我的推断**：我曾用"坐标差两格"推出"摆法不对"，而真实几何是石碑占据两格。教训是——在没有确认方块实际占据范围前，不要下"用户摆错了"的结论。
