# 2026-10-17 操作员编辑与离线玩家名

**状态**：PARTIAL（单测与构建通过；两项实机复测待机主执行 M1/M2）

## 改了什么

1. `block/entity/XpPaymentTankBlockEntity`
   - 新增 `public boolean canEditOrOp(Player)`：`editAllowed(canEdit(player), player.hasPermissions(2))`。
   - 新增包级纯函数 `static boolean editAllowed(boolean ownerOrTeamMate, boolean operator)`。
   - `canEdit` 的 javadoc 改写：它只回答「属主或同队」，OP 例外在 `canEditOrOp`，并写明**为什么**放一起。
2. `net/XppServerHandler:53`：`tank.canEdit(player) || player.hasPermissions(2)` → `tank.canEditOrOp(player)`。
3. `net/XppStatePayload:138`：发给界面的 `canEdit` 字段改用 `tank.canEditOrOp(player)`。
4. 新增 `auth/PlayerNames`：`remembered(MinecraftServer, UUID)`（读 `server.getProfileCache()`，服务器或仓库缺失时返回 `null`）与 `shortId(UUID)`（前 8 位）。
5. `net/XppStatePayload`：`labelForPlayer` 的链条改为 本人名 → 在线名 → 档案缓存名 → 短 id；新增包级纯函数 `static String labelFor(UUID, String onlineName, String rememberedName)` 承担优先级。
6. `auth/FtbTeamsResolver#offlineName`：改为 `PlayerNames.remembered(ServerLifecycleHooks.getCurrentServer(), id)` + `shortId`，删除重复的档案缓存代码与三个失效导入。
7. 测试：`auth/PlayerNamesTest`（2）、`net/XppStateLabelTest`（3）、`block/entity/TankEditRightsTest`（3）。

## 为什么改

D1–D10 实机实测报出两个问题：

- **OP 打开别人（或自己的）罐子，界面按钮全灰**：服务端的编辑闸门是 `canEdit || hasPermissions(2)`，而界面读的是 `XppStatePayload` 打包的 `canEdit`（不含 OP）。同一个规则两处各算一遍，必然分叉。
- **成员下线后名单里显示 36 字符 UUID**：`labelForPlayer` 只问了在线玩家表，人一退出就没有名字来源；队伍成员列表那侧早就有「档案缓存 → 短 id」的回落，两处各写一份，于是一处修了另一处没修。

## 改动前后对比

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 操作员右键别人的罐 | 界面按钮禁用（服务端其实会接受） | 界面可用，服务端一致接受 |
| 名单里某人下线 | 行上显示 `6d1c4a6f-2e4b-4f0f-9a3e-1c2b3a4d5e6f` | 显示 `DrDogey`（档案缓存里记着的名字），缓存也没有时才显示 `6d1c4a6f` |
| 队伍成员列表里的离线成员 | 已是「缓存名 → 短 id」 | 行为不变，但与访问名单共用同一实现 |

## 根因分析

两处「同一事实、两份实现」：

1. **谁能编辑**：服务端算宽版、界面发窄版。修法不是让客户端猜，而是把两个调用方都接到同一个方法上（`canEditOrOp`），窄版 `canEdit` 只作为它的组成部分保留。
2. **玩家叫什么**：`XppStatePayload.labelForPlayer` 与 `FtbTeamsResolver.offlineName` 各有一套回落。修法是抽出 `PlayerNames` 作为唯一的名字来源，优先级（在线 → 缓存 → 短 id）用纯函数表达，可单测。

`PlayerNames.remembered` 的 API 形状来自本仓既有用法（`auth/FtbTeamsResolver.java:189-192` 的 `server.getProfileCache().get(id)`），不是凭记忆假设。
