# 置灰不会恢复（客户端把罐补满后条目仍不可点）— 2026-10-24

## 改了什么

- 新增 `src/main/java/com/olynk/waystonexppayment/client/PaymentGreyState.java`：三态状态机
  `Boolean nextActive(boolean affordable, boolean activeNow)` —— 返回 `FALSE` 表示「置灰」，`TRUE` 表示「把先前置的灰恢复」，
  `null` 表示「别动这个按钮」。它同时记住「这块灰是不是我们的规则造成的」：首帧 `affordable && !active` 才是 Waystones
  自己的理由（比如你就站在这个石碑上），其余情况都归我们管。
- 重写 `src/main/java/com/olynk/waystonexppayment/mixin/WaystoneButtonClientMixin.java`：`renderWidget` 的 HEAD
  不再只会 `active = false`，而是把当前帧的可付性交给 `PaymentGreyState` 决定置灰或恢复；只在状态翻转时打一行
  `[client] greyed out / re-enabled this entry: ...`。
- `src/main/java/com/olynk/waystonexppayment/client/ClientFluidPaymentRequirement.java` 新增
  `describeAffordability(Player)`：把「罐出多少、玩家出多少、总价多少」写进上面那行日志，用于下一次实机取证。
- 新增 `src/test/java/com/olynk/waystonexppayment/client/PaymentGreyStateTest.java`：5 例，覆盖置灰、幂等、恢复、
  「列表在短罐时打开、补满后恢复」、以及「不点亮 Waystones 自己置灰的条目」。

## 为什么改

机主实机反馈：「界面点不了，是灰的。用泵来测试，一样，几乎在流体不足的那一刻立刻界面就变灰了。」

根因是旧版 mixin 的置灰是**单向**的：`renderWidget` 里只有 `widget.active = false`，没有任何写回 `true` 的路径。
Waystones 只在构建条目时算一次 `active`，条目不会因为罐补满而重建，所以任意一帧判定为「付不起」——哪怕是泵在
抽罐的瞬间、或者一次 hint 没读到的瞬时未知——就会让这个条目在本次界面会话里永久不可点，只能关掉列表重开。

客户端日志坐实（单机存档，2026-10-24）：`10:04:15.181 ... pool 3 XP (cost 27 XP)` 之后条目被置灰；
`10:07:18.983 ... pool 28 XP`、`10:07:35.208 ... pool 102 XP`、`11:07:05.801 ... pool 41 XP`（都 ≥ 27，按规则应当可点），
而当天整份日志里**没有任何一条** `Teleport paid from` —— 罐补满也没救回来，一次都没点进去。

## 备选方案与取舍

- **每帧重建条目／强制刷新列表**：能让 `active` 重算，但会和 Waystones 自己的列表管理打架，还会带来滚动位置与焦点丢失、
  每帧重建开销；代价远大于收益，不做。
- **干脆去掉客户端置灰，交给服务端判定**：实现最简单，但 `docs/变更记录/2026-10-10_池子不足时按钮变灰（客户端实时判定）.md`
  定下的设计是「罐不够付这一次就置灰，未知不置灰」，去掉等于让玩家反复点进失败传送，体验倒退；不做。
- **只记住「我们置的灰」再恢复**（最初实现）：能修好「打开界面后抽干再补满」，但修不好「短罐时打开界面、之后补满」——
  那种情况下按钮是 Waystones 在构建时用我们同一个 `canAfford` 关掉的，状态机误判成别人的理由，补满也不恢复。
  这是实机场景里最常见的一半，必须覆盖。
- **采用「灰的归属」判定 + 三态返回值**（最终方案）：首帧 `affordable && !active` 判为他人理由，其余归我们；恢复时只恢复
  自己置的灰，因此「你就在这个石碑上」这类条目不会被点亮。改动集中在一个不依赖 Minecraft 的 47 行小类和 mixin 的 20 行，
  不碰协议、不加依赖、可脱离客户端单测。选它。

## 意外点

- 置灰判定规则本身（`PaymentSplit`：罐出多少 + 玩家出多少）是对的，坏的是「置灰之后没人负责恢复」。
- 第一次实现只记「自己置的灰」，把「短罐时打开界面」漏掉了 —— 写状态机时才发现归属需要从首帧推断，这也说明为什么
  这条规则必须抽成可单测的纯逻辑：五个用例里有两个专门盯归属边界。
- 同一个单向 bug 也会放大瞬时未知：某帧读到过期池量就会永久留下灰色。因此本轮把「为什么灰」写进翻转日志
  （`describeAffordability`：罐 A of B XP、玩家 C of D XP、总价 N XP）。
- 服务端 `payment/FluidPaymentRequirement.consume` 的 `if (!split.affordable()) return;`（不扣费直接放行 = E-1
  零代价窗口）**本轮未改**，与置灰是两回事，留待单独一轮。
