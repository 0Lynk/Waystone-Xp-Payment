# 置灰改为每帧纯派生，并关掉「传送完成但一分没扣」的窗口 — 2026-10-24

## 改了什么

- **删** `src/main/java/com/olynk/waystonexppayment/client/PaymentGreyState.java` 与
  `src/test/java/com/olynk/waystonexppayment/client/PaymentGreyStateTest.java`。置灰不再有跨帧状态，
  也没有「这本灰是不是我置的」的账本。
- `src/main/java/com/olynk/waystonexppayment/mixin/WaystoneButtonClientMixin.java`（77 → 61 行）：
  `renderWidget` HEAD 每帧重新推导一次 `active`——
  `boolean affordable = requirement.canAfford(player); if (widget.active == affordable) return; widget.active = affordable;`，
  只在真的翻转时打一行 INFO。删掉 `@Unique PaymentGreyState` 字段与它的惰性 getter。
- 新增 `src/main/java/com/olynk/waystonexppayment/payment/PaymentSettlement.java`：纯 record
  `(int xpFromTank, int xpFromPlayer, int xpStillOwed)` + `static PaymentSettlement settle(PaymentSplit agreed, int drainedMb, int playerXp)`。
  把「罐实际给出多少 mB → 折成多少 XP → 玩家补多少 → 还欠多少」抽成一个不依赖 Minecraft 的函数，可直接单测。
- `src/main/java/com/olynk/waystonexppayment/payment/FluidPaymentRequirement.java`：
  新增 `@Nullable private PaymentSplit agreed;`。`canAfford` 把批准的 `PaymentSplit` 记进 `agreed`（不通过时置 `null`）；
  `consume` 只结算 `agreed`，不再重算、也不再因重算不可付而 `return`——改为按罐的实际出量结算，缺口由玩家补，
  仍补不上就 `LOGGER.error` 记账（另有 `LOGGER.warn` 处理「罐少给但玩家补齐了」这一不致命的情形）。
- 新增 `src/test/java/com/olynk/waystonexppayment/payment/PaymentSettlementTest.java`（7 例）。

## 为什么改

机主反馈两类问题，源头上是同一件事：「界面显示的那个结论」与「传送时服务器重新得出的结论」不是同一个东西。

1. 置灰永不再亮：上一版用 `PaymentGreyState` 记「这次灰是我置的」，靠首帧快照 `(affordable, activeNow)` 反推归属。
   只要某一帧判负，按钮就死在那次会话里，罐补满也不恢复（G-1）。归属规则本身有损，于是又派生出自目标被点亮（G-2）、
   创造模式被误置灰（G-3）两个补丁。
2. 零代价窗口（E-1）：`consume` 里 `if (!split.affordable()) return;`——`canAfford` 通过、到 `consume` 时罐被拆走或区块卸载，
   重算变不可付就什么都不扣，传送照常完成。同一处的第二个洞是不校验 `drainInternal` 实际扣出多少（`FluidTank.drain`
   会截断），罐只给一半也算付清。

## 备选方案与取舍

- **按原计划 a′ 增加 `WaystoneEntryClientMixin` 捕获基准 `active`**：计划里说「渲染时 `active = base && canAfford`」，
  基准值取自 `WaystoneList$WaystoneEntry.<init>` 的 RETURN 前。落到代码时没有采用，理由是穷举后的新证据：
  `javap -p -c` 扫全 jar 380 个类，`WaystoneButton.active:Z` 的**唯一写入点**就是
  `WaystoneList$WaystoneEntry :: 132: putfield`（「该条目就是玩家脚下的石碑」），`setActive` / `setActiveForRendering` /
  `isActive()` 全 jar 零命中。而对本 mixin 关心的按钮，Waystones 构造器里的另一条置灰理由
  `!canAfford(player) && !instabuild` 与罐的可付性是同一个答案；`player == null` 到不了这里（没玩家就没有 widget）；
  自目标那一条在 `XppClientRequirements.decorate` 早就早退、`instanceof` 不匹配。也就是说基准值永远是 `true`，
  捕获它只是重新推导一个常量。少一个 mixin、少一个 `@Shadow`、少一条注入点，就少一类「上游换了写法就悄悄失效」的依赖。
  **代价**：若 Waystones 将来为非自目标理由置灰条目，本 mixin 会把那条灰覆盖掉。这一条已写进 mixin javadoc，
  且 `MixinShadowPolicyTest` 会在目标类/字段消失时先失败。
- **保留状态机、只补「自动恢复」**（即上一版修法）：能治 G-1，但归属规则本身有损——只要上游出现新的置灰理由，
  就还会产出下一个 G-2/G-3 式反例。选纯派生。
- **在 `consume` 里抛异常或 `setCanceled`**：Waystones 的 `consume` 返回 `void`，异步路径会把异常转成
  `server.execute(throw new RuntimeException("Unexpected error while processing waystone teleport."))`（崩服）；
  `WaystoneTeleportManager` 里 `rollback` **零调用**；`Pre#setCanceled` 在 `canAfford` **之前**，拦不住这一刻的变化。
  所以「事后按实际出量结算 + 记账」是这个 API 下唯一不崩服的选择。
- **真预占（先把流体挪走、失败再还回）**：需要新的方块实体状态与持久化，且预占后玩家掉线会留下悬空流体。
  收益只是把「罐跑了」从可发生降为更不可能，没消掉窗口本身。不选。

## 意外点

- `FluidTank.drain` 会截断：请求 12 mB、罐里只剩 5 mB 时返回的 `FluidStack` 只有 5 mB，而旧代码只看「非空」。
  这条在 E-1 里是第二个洞，`PaymentSettlement` 现在用实际 `getAmount()` 折算。
- `settle` 里玩家的份额必须按「缺口」算，不能按计划里的 `xpFromPlayer`：按计划算就等于「罐少给则免单」，
  这正是旧的零代价窗口换了层皮。负向验证就是按这个形状做的。
- 写第一版单测时踩到自己的断言：`PaymentSplit.compute(10, 100, 10, 0)` 里玩家持 0，缺口应进 `xpStillOwed` 而不是
  `xpFromPlayer`，把它改成玩家持 5 才测出想要的分支。
