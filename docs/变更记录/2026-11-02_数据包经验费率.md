# 变更记录：经验费率改由数据包声明（2026-11-02）

## 改了什么

费率从「配置文件 + 标签 + 名字猜测 + 配方」四套来源并存，改成**唯一来源：数据包配方**。

**新单位**：`xp_per_bucket` —— 一桶（1000 mB）该流体值多少经验，允许小数。内置常量
`XpRate.MILLI_PER_XP = 1000`，内部一律用「千分之一经验 / 桶」的整数保存，任何换算都不经过 float。

## 为什么改

旧的四套来源互相覆盖，且优先级和 README 写的相反：`FluidRates.rebuild` 先放配置文件条目、再 `addAll`
配方条目，`Map.put` 让后者胜。配置 reload 又会走 `rebuildFromConfig()` 把全部配方费率清空——满罐变 0 值、
玩家全款自付，且一条日志都不留。

更要紧的是单位。`mbPerXp` 只能是 ≥1 的整数，比 1 XP/mB 更浓的流体（0.5 mB = 1 XP）根本写不出来；
各路代码都写着 `Math.max(1, rate)` 兜底，把 0.5 静默改成 1 —— 倍率差 500 倍，不报错。费率 1 时五种实现
恰好等价，所以这个问题一直看不见。

## 改动前后对比

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 比 1 XP/mB 更浓的流体 | 写不出来，只能按 1 记，罐子价值被低估 | `"xp_per_bucket": 2000`，1 mB 顶 2 经验，取整方向保证罐子不少付 |
| 配置与配方冲突 | 配方静默赢，README 说配置赢 | 只有一条来源，冲突只发生在多个数据包之间，按包优先级后者胜并打 WARN |
| 配置 reload | 清空配方费率，满罐变 0 值 | 不再有费率可 reload，`/reload` 只重读数据包 |
| 未声明流体 | 按配置的默认率或名字猜测收钱 | 值 0，不能付款，每次尝试一条 WARN 说明是哪个流体 |
| 存档里的远端罐 | 存 `mbPerXp` | 存 milli 费率，旧档按 `1_000_000 / mbPerXp` 换算 |

## 根因分析

「费率」在项目里有五种独立表示（配置 TOML int、数据包 JSON int、存档 NBT、两种包的 VarInt），每种各自
做一次取整；抽取一个换算方法只能消灭「公式写错」，消灭不了「漏改一处」。所以这次不是抽方法，而是把
单位收回成一个值类型 `XpRate`：换算只有一处实现，表示层只负责传这个整数。

## 备选方案

- **a. 只在配置里加一个 `xpPerMb` 浮点键**：不动单位体系，最小改动。否决——配置与数据包仍是两套来源，
  冲突规则照旧说不清。
- **b. 保留标签声明，只把单位换成每桶**：否决——标签与精确 id 同时命中时取哪个从未定义（`byTag` 是
  `Map.copyOf`），这正是玩家报的「同一个流体有时算有时不算」的来源。
- **c. 运行时推算费率**（读别的 mod 的配方）：否决——不可靠，且会把别人的转换率当成事实。
- **d. 保留 `mb_per_xp` 兼容读**：否决——两种单位同时存在，正是这次要消灭的东西；旧包直接解析失败并
  报错，比静默按旧单位记账好。

## 意外点

1. `git ls-files` 之外的一个坑：`Resource#sourcePackId()` 给的是包 id 字符串，而优先级顺序要另外从
   `PackRepository#getSelectedPacks()` 的索引取——两者必须配对，否则「后加载覆盖」就退化成字典序。
2. `XpRate.mbPerXp()` 作为旧单位投影，对浓流体是**有损**的（2000 XP/桶 投影成 1 mB/XP，即少算一半）。
   它只允许出现在显示与旧存档换算里，任何计费路径用它就是错账；本轮把计费路径全部改成直接用 `XpRate`。
3. 客户端在修好之前会拿 `hint.xpPerBucketMilli() == 0` 当「未声明」，因此不能用 `Math.max(1, …)` 兜底，
   否则未声明流体又会被当成 1 XP/mB 去算账。
