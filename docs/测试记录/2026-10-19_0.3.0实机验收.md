## 3. 只有口头、日志无法确认的项

E3、E4、E6 三条都属「静默分支」：设计上拒绝/回退不打日志（`payment/PayerBudget` 失手静默、`U-2` 明确不加日志），因此**用日志证不了、只能靠前后数据快照**。这三条现在记的是「口头通过 + 无定量证据」，不是「已验证」。

补证成本很低（一次即可覆盖三条）：传送到半途失败前 `/data get block` + `/xp query`，失败后同两条命令再各执行一次。

## 6. E8 判定：**未测（环境受限）**，不是「不需要测」

**判定：未测（环境受限）**。理由三条：

1. **它守的是仍开着的东西**。E8 唯一目标是 `E-1`（付款判定读活状态 + 静默返回 → 零代价传送窗口），而 `E-1` 在 `问题修复清单.md` 里**至今未修**。缺陷还在，验收路径就不能划掉。
2. **环境其实不构成硬阻断**。正式服 + 两个客户端（`1.21.1` 与 `1.21.1-fork`）都已部署同一 jar，两个账号同时在线是现成条件；「苛刻」指的是命中「几乎同时」这个时间窗，不是缺设备。因此记「环境受限（需要双人同 tick 并发）」比记「不需要测」诚实，也比记「无法测」准确。
3. **低成本的替代验证**（不改源码也能做，按性价比排序）：
   - 两人站在同一石碑、同一秒内各点一次（目视 + 事后对 `/xp query` 与罐池量求和，看总扣费是否 == 总花费）；
   - 或对已知开源时序做一次静态论证：付款判定与扣费之间若读的是活状态，则「判定通过 → 另一线程抽干 → 扣费静默失败」窗口在构造上存在 —— 这条只能说明窗口存在，不能替代实测；
   - 若两者都不做，就把 `E-1` 写进 Release note 的「已知限制」，并在验收结论里保留「E8 未覆盖」。

**不接受**把 E8 记为「不需要测」：那等于用一个未测项去背书一个未修缺陷。
