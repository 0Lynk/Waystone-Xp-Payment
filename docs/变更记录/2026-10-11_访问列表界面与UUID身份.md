# 2026-10-11 访问列表界面与 UUID 身份

## 改了什么

- 界面重写：`client/XpPaymentTankScreen.java` — 从"扁平按钮 + 两行名字文本"改为 256×214 面板：
  模式切换按钮 + `+ 添加我`、流体条、可点击的**访问列表**（5 行可见、滚轮滚动、3px 滚动条、
  行内 `×` 删除、悬停出 UUID 提示）。列表是画出来的，不是 widget 树（见类注释里的假设说明）。
- 身份改为 UUID：`auth/AccessList.java` — 主存 `Set<UUID> players` / `Set<UUID> teams`，
  白名单标志保留；旧的名字条目降级为 `legacyPlayers` / `legacyTeams` 只读兼容集，
  `allows()` 按"玩家 UUID → 所在队伍 UUID → 旧名字（仅当存在旧条目时，忽略大小写）"三级匹配。
  `save()`/`load()` 写 `playerUuids`/`teamUuids`（`NbtUtils.createUUID` 的 int-array 列表）+
  两个旧名字列表，并额外提供 `readPreviousFormat()` 读取旧世界的 `players`/`teams` 复合列表做迁移。
- 协议：`net/XppStatePayload.java` 改为携带**一条合并列表** `List<Entry>`（`Entry(id, label, team, mine)`，
  `team` 只是渲染标志）+ `ownTeams()`；UUID 用 `UUIDUtil.STREAM_CODEC` 编码。
  `net/XppAccessPayload.java` 改为 `action + UUID target + String label(≤64)`（label 只用于日志与旧条目删除，
  绝不作为身份解析），`SET_MODE`/`REFRESH` 送零 UUID。
- 服务端：`net/XppServerHandler.java` — 保留"重新校验方块实体 + `hasPermissions(2)`"；
  `ADD_PLAYER` 只接受发送者自己的 UUID，`ADD_TEAM` 只接受发送者所在队伍的 UUID；
  删除同时按 UUID 和 label 删（旧名字条目才删得掉）；每次改动 INFO 记 UUID + label。
- 命令：`command/XppCommands.java` — `addplayer` 先查在线玩家再查 profile 缓存，离线且无档案时明确报错；
  `addteam` 按队伍名在 `TeamResolvers` 里解析成 UUID；`info` 只打印计数 + 至多 8 条条目标识（不再列名字）。
- 语言：`assets/waystone_xp_payment/lang/en_us.json`、`zh_cn.json` — 各 18 键，原有键全保留，
  新增 `access.mode*`、`access.add_me`、`access.pool_xp`、`access.list_header`、`access.list.empty`、
  `access.waiting`、`access.tooltip.*`、`commands.waystone_xp_payment.unknown_player`。

## 为什么改

1. 旧界面把"谁被授权"和"授权/取消"混在一排按钮里，队伍一多就挤成两行文本，无法逐条增删；
   列表化之后每一条自带删除入口，多出来的条目靠滚动容纳。
2. 用名字当身份是错的：改名即失效、重名会串号、离线的旧条目查不到。玩家用游戏档案 UUID、
   队伍用 FTB Teams `Team.getId()` 的 UUID，都是游戏/模组里本来就存在的主键，不需要自造一套 ID。
3. 旧世界已经按名字存了授权，直接换格式会让既有储罐突然停止付款 → 保留 legacy 名字集只读兼容，
   并保证它仍然可见、可删。
4. 客户端发来的 label 是不可信文本，只能当日志和"顺手删掉同名旧条目"用，因此 `ADD_PLAYER`/`ADD_TEAM`
   一律用发送者自己的 UUID 与自己的队伍表重新验证，不信任客户端给的任何身份。

## 根因分析与教训

1. **别把展示名当主键**：这次是"名字 → UUID"的迁移。教训是只要一个系统里存在稳定 ID
   （`player.getUUID()`、`Team.getId()`），任何持久化的授权/关系都应该存 ID，展示名只用于渲染。
2. **兼容旧数据要留"只读降级"路径**：旧条目无法反推 UUID（改名/离线都会丢），所以不能假装能迁移完，
   只能保留并让它继续生效；否则"升级即断付"是比格式不统一严重得多的回归。
3. **一次性写完的代码也要单独验证序列化**：本轮用离线探针（`AccessRoundTrip`）跑 save/load 往返、
   旧格式迁移、空 tag、畸形 tag 共 16 项断言 —— 正是这个探针抓到了 `save()` 在遇到 null id 时
   抛 `NullPointerException`（`UUIDUtil.uuidToIntArray(null)`）的真实崩溃，随后加了跳过与
   `addTeam(@Nullable UUID)` 的空值短路。**序列化代码不跑一次往返就等于没写。**
4. **空洞流体栈不能用非可选 codec**：`FluidStack.STREAM_CODEC` 在空罐上抛
   `Empty FluidStack not allowed` → `EncoderException` → 掉线；必须用 `OPTIONAL_STREAM_CODEC`。
   这是实机踩到的，已在代码注释里记明。
5. **本机验证的边界**：本环境不允许跑 gradle，因此构建/单测未执行；改用外部 curated classpath
   对全部 35 个源文件做了一次离线 `javac`（退出码 0）作为"至少能编译"的证据（详见下方状态块）。
